> **このドキュメントの位置づけ**
> アプリが自動で計算する値（pips・損益（円）・リスクリワード）の「正解」を決める文書です。`js/calc.js` はこの文書の式どおりに実装し、9章のテストケースを全件満たすことを完了条件とします（T-13・T-14）。
> 本アプリは**記録・振り返り用のツール**です。この文書は「記録された数値をどう計算するか」だけを定めており、売買の判断や推奨には一切関係しません。

## 1. この文書で使う用語

| 用語 | 一言説明 |
|---|---|
| 通貨ペア | 2つの通貨の組み合わせ。`USD/JPY` なら「1ドルが何円か」を表す |
| 基軸通貨・決済通貨 | `USD/JPY` の左側（USD）が基軸通貨、右側（JPY）が決済通貨（クオート通貨とも言う）。**価格は決済通貨の単位**で表され、**損益もまず決済通貨で発生する** |
| JPYペア | 決済通貨が円（右側が `JPY`）のペア。例：USD/JPY、EUR/JPY、GBP/JPY、AUD/JPY |
| 非JPYペア | 決済通貨が円以外のペア。例：EUR/USD（決済通貨はUSD）、GBP/USD、EUR/GBP（決済通貨はGBP） |
| pip（ピップ）／pips | 値幅の単位。JPYペアは 0.01円＝1pip、非JPYペアは 0.0001＝1pip。複数形が pips |
| ポイント（0.1pip） | 本文書での内部計算用の最小単位。1ポイント＝0.1pip。JPYペアは 0.001、非JPYペアは 0.00001。業者アプリの価格の最後の1桁（例 150.12**3** の「3」）にあたる。業者によっては「ピペット」「point」と呼ぶ |
| 約定価格 | 実際に売買が成立した価格。スプレッド（買値と売値の差）は約定価格にすでに含まれている |
| ロット（lot）／lotUnitSize | 取引数量の単位。1lotが何通貨か（`lotUnitSize`）は業者により異なるため設定値（初期値1万通貨、Q-01） |
| 取引数量（通貨数） | `ロット × lotUnitSize`。例：0.5lot × 1万通貨 ＝ 5,000通貨 |
| 円換算レート | 非JPYペアの損益（決済通貨建て）を円に直すためのレート（`quoteToJpyRate`）。EUR/USD なら USD/JPY の値 |
| 浮動小数点誤差 | コンピュータが小数を2進数で近似するために生じるごく小さなズレ。JavaScriptでは `0.1 + 0.2` が `0.30000000000000004` になる |
| 整数化 | 小数の価格を「ポイント（整数）」に直してから計算すること。整数の足し算・引き算・掛け算には誤差が出ないため、誤差対策の基本とする |
| 四捨五入（0から遠い方へ） | 端数がちょうど0.5のとき、絶対値が大きくなる方へ丸める。+1.5→+2、−1.5→−2。本文書の「四捨五入」はすべてこの意味 |
| BigInt | JavaScriptで桁数の大きい整数を誤差なく扱う型（`123n` のように書く）。iOS Safari 14以降・Android Chrome で使える |
| エラー／警告 | エラー＝保存させない入力ミス。警告＝注意を表示するが保存はできるもの |

## 2. 前提と計算の対象範囲

| 項目 | 内容 | 根拠 |
|---|---|---|
| 口座通貨 | 日本円固定。損益は円で表示・保存する | Q-09 |
| 取引の単位 | 1エントリー＝1決済。分割決済・ナンピンは記録を分けて登録 | Q-04 |
| 価格 | 業者アプリに表示された**約定価格**をそのまま入力する（スプレッドは約定価格に含まれる） | — |
| スワップポイント・手数料 | 自動計算には**含めない**。含めたい場合は業者の確定損益で上書きする（4.4） | Q-03 |
| 1lotの通貨数 | 記録時点の設定値を各記録の `lotUnitSize` にコピーし、以後の計算はその値を使う。設定を変えても過去の記録は再計算しない。**例外：編集で口座区分（デモ⇔本番）を変えたときだけ、変更先の口座区分の現在の設定値をコピーし直す**（4.5） | Q-01、requirements 5.2 F-08、architecture 20章（2026-10-15 決定） |
| 1lotの通貨数の単位 | 口座区分（デモ/本番）ごとに1つの値。**通貨ペアごとの1lot設定は作らない**（高金利通貨を取引しないため。10.6） | 14章 #7（2026-10-15 決定） |
| 時刻 | 日本時間（JST）基準 | Q-08 |
| 対象商品 | FX通貨ペアのみ（ゴールド等は対象外） | Q-05 |

> **自動計算値と業者の確定値がずれることがあります。** 円換算に使うレートの種類や時点、円未満の端数処理、手数料の有無などは**業者により異なる**ためです。正確な値を残したい場合は、業者アプリの確定損益で上書きします（4.4）。

## 3. pips の計算

### 3.1 pip単位の決め方

| 区分 | 判定方法（T-02時点） | 1pip | 1ポイント（0.1pip） | 入力できる価格の小数桁 |
|---|---|---|---|---|
| JPYペア | `pair` の `/` の右側が `JPY` | 0.01 | 0.001 | 小数第3位まで |
| 非JPYペア | 上記以外 | 0.0001 | 0.00001 | 小数第5位まで |

- 判定は T-02 時点では通貨ペア文字列で行います。T-03 で通貨ペアマスタ（ペアごとの pip単位・表示桁数）を定義したら、**マスタの値を優先**します。一部の新興国通貨ペアなど、例外的な pip単位を使うペアがある場合はマスタ側で個別に定義します（pip単位の慣習は**業者により異なる**場合があります）。→ **T-03 で定義済み（10章）**。マスタの19ペアはすべて上表のルールと同じ値です。
- 業者によっては JPYペアを小数第2位、非JPYペアを小数第4位までしか表示しません。その場合も上限以内なのでそのまま入力できます。

### 3.2 売買方向と符号

| 売買方向 | 意味 | 値幅（決済通貨建て） | pips がプラスになるのは |
|---|---|---|---|
| 買い（`buy`、ロング） | 先に買って、後で売る | 決済価格 − エントリー価格 | 価格が上がったとき |
| 売り（`sell`、ショート） | 先に売って、後で買い戻す | エントリー価格 − 決済価格 | 価格が下がったとき |

- **pips・損益ともに「プラス＝利益、マイナス＝損失」** で統一します。

### 3.3 計算手順（整数化して計算する）

1. 価格をポイント（整数）に直す：`ポイント = 四捨五入(価格 × 倍率)`
   - 倍率：JPYペア **1,000**、非JPYペア **100,000**
   - 入力桁数が上限以内（8章）なので、この四捨五入で正確な整数になります（掛け算で出たごく小さな誤差を消すための四捨五入です）
2. 値幅ポイント（`diffPoints`）を求める
   - 買い：`diffPoints = 決済ポイント − エントリーポイント`
   - 売り：`diffPoints = エントリーポイント − 決済ポイント`
3. `pips = diffPoints ÷ 10`（結果は必ず小数第1位までの値になる）

**例**：USD/JPY 買い、エントリー 150.500、決済 150.123
エントリー 150,500ポイント、決済 150,123ポイント → diffPoints = −377 → **pips = −37.7**

## 4. 損益（円）の計算

### 4.1 取引数量

```
取引数量（通貨数） = lots × lotUnitSize
```

- 内部計算では `lots` を100倍して整数にします（`lotsX100 = 四捨五入(lots × 100)`）。ロットは小数第2位まで入力可（8章）なので正確な整数になります。
- 例：0.07lot → `0.07 × 100` はJavaScriptでは `7.000000000000001` になるが、四捨五入して `7` とする。

### 4.2 JPYペア

```
損益（円） = 値幅（円） × lots × lotUnitSize
```

- 整数化した計算式（参照実装 6.4 と同じ）
  `損益（円） = 四捨五入( diffPoints × lotsX100 × lotUnitSize ÷ 100,000 )`
  （100,000 ＝ ポイント→円の 1,000 × ロットの100倍の 100）
- 例：USD/JPY、1万通貨（1lot × 10,000）で 1pip（0.01円）動くと 100円。25pips なら 2,500円。

### 4.3 非JPYペア（円換算レート `quoteToJpyRate`）

```
損益（円） = 値幅（決済通貨） × lots × lotUnitSize × quoteToJpyRate
```

| ペアの例 | 決済通貨 | 円換算レートに入れる値 |
|---|---|---|
| EUR/USD、GBP/USD、AUD/USD | USD | USD/JPY のレート |
| EUR/GBP | GBP | GBP/JPY のレート |
| USD/CHF | CHF | CHF/JPY のレート |

- **円換算レートが入力されている場合**：上の式で自動計算する（`profitSource = auto`）。
  整数化した計算式：
  `損益（円） = 四捨五入( diffPoints × lotsX100 × lotUnitSize × rateX1000 ÷ 10,000,000,000 )`
  （`rateX1000 = 四捨五入(quoteToJpyRate × 1,000)`。割る数 = ポイントの 100,000 × ロットの 100 × レートの 1,000）
- **円換算レートが空欄の場合**：損益（円）は自動計算できない。決済を保存するには**損益（円）の手入力が必須**（`profitSource = manual`）。pips は通常どおり自動計算する。
- 円換算レートは**決済時点**の「決済通貨/JPY」レートを目安とします。どのレート（買値・売値・仲値）で、どの時点（決済時・日次の締め時など）に円換算するかは**業者により異なる**ため、自動計算値は参考値です。業者の確定値に合わせたい場合は手入力で上書きします。
- JPYペアでは円換算レートは使いません（入力欄を出さない、または保存時に `null` とする）。
- 掛け算の途中結果が JavaScript の通常の数値で正確に扱える上限（`Number.MAX_SAFE_INTEGER`、約9×10^15）を超えることがあるため（例：テストケース C-16）、**損益の掛け算は BigInt で行います**。

### 4.4 手入力による上書き（`profitSource = manual`）

| 場面 | ルール |
|---|---|
| 上書きの方法 | 決済画面・編集画面で損益（円）欄を直接入力すると `profitSource = manual` になり、入力値を `profitJpy` に保存する |
| 入力できる値 | **整数の円**（マイナス・0も可）。カンマ（`-5,700`。全角の `，` も）は取り除いて受け付ける。業者アプリの表示を写した先頭の `+`（`+2,480`。全角の `＋` も）も受け付ける（2026-10-16 決定。8.1）。小数はエラー |
| 自動計算との関係 | `manual` の記録は、価格・ロット等を編集しても `profitJpy` を**自動で書き換えない**。画面には参考として自動計算値（計算できる場合）を並べて表示する |
| 自動に戻す | 「自動計算に戻す」操作で `profitSource = auto` にし、`profitJpy` を自動計算値で置き換える（非JPYペアで円換算レートが空欄なら戻せない） |
| pips | pips は常に自動計算（手入力の上書きはしない） |
| 勝敗判定・集計 | 保存されている `profitJpy`（手入力値を含む）を使う（7章） |
| 符号のずれ | 手入力値と pips の符号が逆（例：+0.5pips なのに −30円）の場合は警告を出す。スワップ・手数料の影響ならそのまま保存してよい |

### 4.5 再計算と決済取り消し時の扱い

- **再計算のタイミング**：`pair`・`side`・`entryPrice`・`exitPrice`・`lots`・`quoteToJpyRate`・`slPrice`・`tpPrice`・`accountType`（下記の `lotUnitSize` の取り直しを伴う）のいずれかが変わったとき、pips・損益（`auto` のときのみ）・RR を再計算する。
- **`lotUnitSize`**：記録時点の値を使う。設定画面で1lotの通貨数を変えても、既存の記録は再計算しない。
- **編集で口座区分（`accountType`）を変えたとき**（2026-10-15 決定）：口座区分の変更は入力ミスの修正と考えられるため、`lotUnitSize` を**変更先の口座区分の現在の設定値でコピーし直し**、`profitSource = auto` の記録は損益（円）を再計算する。**`profitSource = manual`（業者の確定値で上書き）の記録は `profitJpy` を書き換えない**（4.4 の「manual は自動で書き換えない」と同じ扱い）。値が変わるときは画面で「1lotの通貨数を 10,000 → 100,000 に変更しました」のように知らせる（architecture 8章）。保存前に**元の口座区分に戻した場合は、`lotUnitSize` も記録時の値に戻す**（押し間違いを元どおりにするため。design 14.5.3）。
- **編集で通貨ペアを変えたときの円換算レート**（2026-10-16 **決定（推奨案）**。fx-expert が T-22 の確認で提案した内容を、オーナー未回答のため推奨案のまま確定した。異論があれば変更する。実装済み：`js/edit-form.js` の `rateAfterPairChange`）：`quoteToJpyRate` は「決済通貨/JPY」のレートなので、EUR/USD（USD/JPY）→ EUR/GBP（GBP/JPY）のように円換算ペア（`quoteToJpyPair`）が変わると、古いレートは別の通貨のレートになる。そのまま自動計算に使うと損益（円）が誤るため、次のとおり扱う。
  1. **円換算ペアが変わらない**（決済通貨が同じ。EUR/USD → GBP/USD など）：今のレートを**残す**。
  2. **円換算ペアが変わる**（決済通貨が変わる。JPYペア ⇔ 非JPYペアの変更を含む）：レート欄を**空にする**。`profitSource = auto` の記録は、保存時に E-11 で入れ直しを促す。**手入力（`manual`）の損益は書き換えない**。JPYペアにしたときの保存値は `null`（4.3）。
  3. **変更したあとに、記録を開いたときのペアの円換算ペアへ戻した**：**記録のレートに戻す**（押し間違いを元どおりにする。口座区分を戻したときの `lotUnitSize` と同じ考え方）。
- **保有中（`open`）の記録**：`pips`・`profitJpy`・`profitSource` は空（`null`）。RR はエントリー時点で計算できる。
- **計算に必要な値が空のとき（2026-10-16 オーナー決定・14.2 #5）**：`calcPips`・`calcProfitJpy` は、必要な値が空（`null`・`undefined`＝未入力）なら意味のない値を返さず**空（`null`）を返す**。保有中の記録や、入力途中の画面（決済価格をまだ入れていない等）で呼んでも安全にするため。
  - 「必要な値」：`calcPips` は `pair`・`side`・`entryPrice`・`exitPrice`。`calcProfitJpy` はそれに加えて `lots`・`lotUnitSize`（非JPYペアは `quoteToJpyRate` も。これは従来どおり空なら `null`）。
  - 戻り値の形：`calcPips` は**形を変えずに中身を空にする**（`{ diffPoints: null, pips: null }`。呼び出し側が `.pips` をそのまま読めるように）、`calcProfitJpy` は `null`。
  - 変更前の動き（T-14 で確認）：決済価格が空だと pips −15000.0、ロットが空だと損益 0円、1lotの通貨数が空だと例外。テストケース C-18〜C-20（14.1）で確認する。
  - 実装は engineer が T-11 と同時に行う（roadmap T-11）。
- **決済の取り消し（`open` に戻す）**：計算に関わる `exitPrice`・`exitAt`・`pips`・`profitJpy`・`profitSource`・`quoteToJpyRate` を空（`null`）に戻す。決済理由・決済時の感情・メモ・タグ・画像は**残す**（14章 #5 で決定。requirements F-02）。

## 5. リスクリワード（RR）

### 5.1 計算式

SL・TP の**両方**が入力されているときだけ計算します（どちらかが空なら `riskReward = null`、警告なし）。

> 通貨ペア・売買方向・エントリー価格が空（入力途中）のときの扱いは、**5.3**（確定：2026-10-16 オーナー決定）を参照。

| 売買方向 | 損切り幅（リスク） | 利確幅（リワード） | 正しい並び |
|---|---|---|---|
| 買い | エントリー − SL | TP − エントリー | SL ＜ エントリー ＜ TP |
| 売り | SL − エントリー | エントリー − TP | TP ＜ エントリー ＜ SL |

```
RR = 利確幅 ÷ 損切り幅   （小数第2位に四捨五入）
```

- 価格は 3.3 と同じくポイント（整数）に直してから差を取ります。
- 正しい並びのときは `requirements.md` 6章の式（絶対値どうしの割り算）と同じ結果になります。
- 例：買い、エントリー 150.000、SL 149.800（損切り幅 20.0pips）、TP 150.400（利確幅 40.0pips）→ RR = **2.00**
- 損切り幅・利確幅を **pips で表示するとき**（画面の「損切り 20.0 pips・利確 40.0 pips」）は、上の表のポイント差を 10 で割ります（6.1・6.4 の `calcSlTpPips`）。RR が出ないとき（必要な値が空、または W-01）は幅も出さず、どちらも `null`（9.2 の R-06〜R-09 の「—」）。

### 5.2 SL/TP が売買方向と矛盾するとき

損切り幅または利確幅が **0以下** になる場合（＝正しい並びになっていない場合）は、次のように扱います。

| 状況 | 例 | 扱い |
|---|---|---|
| SL が利益側にある、またはエントリーと同値 | 買いなのに SL ≧ エントリー | **警告を表示するが保存は止めない**。SL/TP の価格はそのまま保存し、`riskReward = null`（RR は「—」表示） |
| TP が損失側にある、またはエントリーと同値 | 売りなのに TP ≧ エントリー | 同上 |

- `null` にする理由：損切り幅が0以下だと「リスクに対するリワード」という比率の意味が成り立たず、分析（RR別の集計）に不自然な値が混ざるのを防ぐため。
- 保有中に SL を建値（エントリー価格）以上へ動かした場合など、**意図的にこの並びになることもある**ため、警告文はやわらかくします。
  - 文言例：「買いなのに損切りライン（SL）がエントリー価格以上です。SLを建値以上に動かした場合はこのままで問題ありません。」
  - 文言例：「売りなのに利確ライン（TP）がエントリー価格以上です。入力内容をご確認ください。」

### 5.3 エントリー価格・売買方向・通貨ペアが空のとき（確定・2026-10-16 オーナー決定）

> **状態：確定**（2026-10-16 オーナー決定：fx-expert の推奨案どおり。T-11 ⑨ の確認時に engineer の報告を受けて fx-expert が作成）。roadmap T-18 の「エントリー価格が空のときの RR の扱い」に当たる。実装側の作業は T-18 で**実施済み**（2026-10-16）：①`js/calc.js` の `calcRiskReward` を直した ②6.4 の参照実装を下の内容に更新した（v1.8） ③下の Y-08〜Y-13 を正式なテストケースとして `tests/cases.js` に転記し、合格を確認した。

**確定した扱い**：`calcRiskReward` は、計算に必要な値（`pair`・`side`・`entryPrice`・`slPrice`・`tpPrice`）の**どれか1つでも空（`null`・`undefined`）なら `{ rr: null, warn: [] }`** を返す（RR は「—」、W-01 は出さない）。`calcPips` の空の判定（4.5）と同じ `isBlank` を使う。

**FX の観点からの理由**

1. 損切り幅・利確幅は「エントリー価格からの距離」で、正しい並び（5.1 の表）も売買方向で決まる。エントリー価格か売買方向が分からなければ、RR も「SL/TP が方向と矛盾しているか」も**判断できない**。判断できないものを警告すると、正しく入力している途中の人に「間違っている」と伝えることになる。
2. 現在の実装（＝ 6.4 の参照実装どおり）では、空の値が次のように扱われてしまう（2026-10-16 fx-expert が実測）。

| 入力（USD/JPY、SL・TP あり） | いまの結果 | 起きていること |
|---|---|---|
| 買い・エントリー価格 `null`・SL 149.800・TP 150.400 | `rr: null`・警告 SL | エントリー価格を 0 とみなすため、買いでは**必ず SL の警告**が出る |
| 売り・エントリー価格 `null`・SL 150.200・TP 149.600 | `rr: null`・警告 TP | 同じ理由で、売りでは**必ず TP の警告**が出る |

| 売買方向 `null`・エントリー 150.000・SL 150.200・TP 149.600（売りの並び） | `rr: 2.00` | 方向を選んでいないのに RR が表示される |

3. エントリー画面では**売買方向は毎回未選択**（roadmap T-17）で、SL/TP の RR は1文字ごとに再計算する（design 14.1.7）。上の表の状態は「方向を選ぶ前に SL/TP を入れた」「エントリー価格を消して打ち直している」といった**ふつうの入力途中で頻繁に起きる**。

## 6. 丸めと浮動小数点誤差の対策

### 6.1 丸め桁数の一覧

| 値 | キー名 | 保存する桁 | 丸め方 | 表示例 |
|---|---|---|---|---|
| pips | `pips` | 小数第1位 | 整数化計算により丸め不要（`diffPoints ÷ 10`） | `+25.0 pips` / `-37.7 pips` / `0.0 pips` |
| 損益（円） | `profitJpy` | 整数 | 四捨五入（0から遠い方へ） | `+2,500円` / `-1,885円` / `0円` |
| リスクリワード | `riskReward` | 小数第2位 | 四捨五入 | `2.00` / `0.33` |
| 損切り幅・利確幅（表示用） | 保存しない | 小数第1位 | 整数化計算により丸め不要 | `20.0 pips` |
| 円換算レート | `quoteToJpyRate` | 入力値のまま（小数第3位まで） | 丸めない | 保存値 `149.85`／画面は円換算ペア（例 USD/JPY）の表示桁数で `149.850`（10.7 `formatPrice(rate, quoteToJpyPair)`。design 14.4.4） |

- 上表の「表示例」は**計算結果の値の形**を示すもので、保存値・CSV では通常の `-`（半角ハイフン）と数値を使います。**画面に出すときの符号・記号は `docs/design.md` 6.3 が正**です：`＋2,500円` / `−1,885円` / `±0円`、`＋25.0 pips` / `−37.7 pips` / `±0.0 pips`（画面のマイナスは「−」U+2212、ゼロは「±0」）。
- **マイナスゼロを作らない**：JavaScriptには `-0` があり、表示で `-0円` になることがある。計算結果が0のときは必ず `0` にする（参照実装の BigInt 計算では `-0` は発生しない）。

### 6.2 丸め方の定義

- **四捨五入（0から遠い方へ）**：`+1.5 → +2`、`-1.5 → -2`、`+1.4 → +1`、`-1.4 → -1`。
- JavaScript の `Math.round` は `Math.round(-1.5) = -1`（プラス方向に丸める）なので、**マイナスの値にそのまま使わない**。
- 円未満の端数処理（四捨五入・切り捨てなど）は**業者により異なる**ため、自動計算値が業者の確定値と1円程度ずれることがあります。正確に合わせたい場合は手入力で上書きします。

### 6.3 誤差対策の方針

| # | ルール | 理由 |
|---|---|---|
| 1 | 価格は**ポイント（整数）に直してから**差を取る | 小数の引き算のまま計算すると `1.10030 − 1.10000 = 0.00029999999999996696` のようなズレが出る |
| 2 | 損益は「整数どうしの掛け算 → **最後に1回だけ**割り算して丸める」 | 途中で何度も丸めると、端数がちょうど0.5のときに結果が1円ずれる（C-11、C-14） |
| 3 | 損益の掛け算は **BigInt** で行う | 大きな数量・値幅で通常の数値の安全な上限（約9×10^15）を超えるため（C-16） |
| 4 | RR は整数（ポイント）どうしの割り算を、整数演算で小数第2位に四捨五入する | `Math.round(x * 100) / 100` では 0.625 が 0.62 になることがある（R-04、R-05） |
| 5 | 計算結果どうしを `===` で直接比べない。**整数（ポイント・円・RR×100）に直してから比べる** | 例：`(150.3 − 150.1) × 3000` は `600.0000000000512` になり、`600` と一致しない（C-15） |
| 6 | 合計値は、pips を `四捨五入(pips × 10)` で整数に戻して足し、最後に10で割る。円は整数なのでそのまま足す | 小数の足し算を繰り返すと誤差が積み重なる |
| 7 | 桁数のチェックは**入力文字列**で行う（数値に変換した後ではなく） | `1.10` は数値にすると `1.1` になり、元の桁数が分からなくなるため |

### 6.4 参照実装（JavaScript）

engineer はこの関数と**同じ結果**になれば書き方は自由です。テストページ（T-13）ではこの結果と9章の期待値を照合します。

- v1.5（2026-10-16 オーナー決定・4.5）で、`calcPips`・`calcProfitJpy` の先頭に「必要な値が空なら `null`」の判定を追加しました（`isBlank` の行）。値がそろっているときの計算は変わらないため、9章の期待値はすべてそのままです。
- v1.8（2026-10-16・T-18。5.3 の確定を反映）で、`calcRiskReward` の先頭を「通貨ペア・売買方向・エントリー価格・SL・TP のどれかが空なら `{ rr: null, warn: [] }`」に置き換えました（`isBlank` を使う）。値がそろっているときの計算・警告は変わらないため、9.2 の期待値はすべてそのままです。追加のテストケース Y-08〜Y-13 は 5.3 の表（`tests/cases.js` に転記済み）。
- v1.8（同・T-18）で、損切り幅・利確幅（pips）を求める `calcSlTpPips` を参照実装に追加しました。5.1 の表の幅（ポイント差）を 10 で割るだけで、丸めはありません。必要な値（pair・side・entryPrice・slPrice・tpPrice）のどれかが空、または損切り幅・利確幅が0以下（W-01）のときは両方 `null` です。9.2 の「損切り幅」「利確幅」の列（R-01〜R-09。R-06〜R-09 は「—」＝`null`）の期待値を満たします。新しい計算式ではなく、表示用の値です（保存しない：6.1）。

```js
// JPYペアかどうか（T-03 以降は通貨ペアマスタの値を優先する）
const isJpyPair = (pair) => pair.split('/')[1] === 'JPY';
// 1ポイント（0.1pip）あたりの倍率：JPYペア 1,000 / 非JPYペア 100,000
const pointScale = (pair) => (isJpyPair(pair) ? 1000 : 100000);
// 価格 → ポイント（整数）。入力桁数が上限以内なら正確な整数になる
const toPoints = (price, pair) => Math.round(price * pointScale(pair));
// 未入力（null・undefined）かどうか（v1.5 で追加）
const isBlank = (v) => v == null;

// pips（小数第1位）。必要な値が空なら { diffPoints: null, pips: null }（4.5。v1.5 で追加）
function calcPips(t) {
  if ([t.pair, t.side, t.entryPrice, t.exitPrice].some(isBlank)) return { diffPoints: null, pips: null };
  const e = toPoints(t.entryPrice, t.pair);
  const x = toPoints(t.exitPrice, t.pair);
  const diffPoints = t.side === 'buy' ? x - e : e - x;
  return { diffPoints, pips: diffPoints / 10 };
}

// BigInt の割り算を「0から遠い方へ四捨五入」する
function divRoundHalfAwayFromZero(num, den) {
  const neg = num < 0n;
  const a = neg ? -num : num;
  const q = (2n * a + den) / (2n * den); // BigInt の割り算は切り捨て
  return Number(neg ? -q : q);           // BigInt に -0 はないので 0 は 0 になる
}

// 損益（円）。非JPYペアで円換算レートが無ければ null（手入力が必要）
// 必要な値（価格・ロット・1lotの通貨数など）が空でも null（4.5。v1.5 で追加）
function calcProfitJpy(t) {
  const { diffPoints } = calcPips(t);
  if (diffPoints == null || isBlank(t.lots) || isBlank(t.lotUnitSize)) return null;
  const lotsX100 = Math.round(t.lots * 100);
  let num = BigInt(diffPoints) * BigInt(lotsX100) * BigInt(t.lotUnitSize);
  let den = 1000n * 100n;
  if (!isJpyPair(t.pair)) {
    if (t.quoteToJpyRate == null) return null;
    num *= BigInt(Math.round(t.quoteToJpyRate * 1000));
    den = 100000n * 100n * 1000n;
  }
  return divRoundHalfAwayFromZero(num, den);
}

// リスクリワード（小数第2位）。方向と矛盾するときは rr=null と警告対象を返す
// 必要な値（pair・side・entryPrice・slPrice・tpPrice）のどれかが空なら { rr: null, warn: [] }（5.3。v1.8 で更新）
function calcRiskReward(t) {
  // 必要な値が空なら RR も W-01 も判断できないので、何も出さない（5.3）
  if ([t.pair, t.side, t.entryPrice, t.slPrice, t.tpPrice].some(isBlank)) return { rr: null, warn: [] };
  const e = toPoints(t.entryPrice, t.pair);
  const sl = toPoints(t.slPrice, t.pair);
  const tp = toPoints(t.tpPrice, t.pair);
  const risk = t.side === 'buy' ? e - sl : sl - e;
  const reward = t.side === 'buy' ? tp - e : e - tp;
  const warn = [];
  if (risk <= 0) warn.push('SL');
  if (reward <= 0) warn.push('TP');
  if (warn.length) return { rr: null, warn };
  // 整数演算で四捨五入：floor((200×reward + risk) / (2×risk)) / 100
  return { rr: Math.floor((200 * reward + risk) / (2 * risk)) / 100, warn };
}

// 損切り幅・利確幅（pips・小数第1位。表示用で保存しない）。RR が出ないとき（空・W-01）は両方 null（v1.8 で追加）
function calcSlTpPips(t) {
  const none = { riskPips: null, rewardPips: null };
  if ([t.pair, t.side, t.entryPrice, t.slPrice, t.tpPrice].some(isBlank)) return none;
  const e = toPoints(t.entryPrice, t.pair);
  const sl = toPoints(t.slPrice, t.pair);
  const tp = toPoints(t.tpPrice, t.pair);
  const risk = t.side === 'buy' ? e - sl : sl - e;
  const reward = t.side === 'buy' ? tp - e : e - tp;
  if (risk <= 0 || reward <= 0) return none;
  return { riskPips: risk / 10, rewardPips: reward / 10 }; // ポイント÷10。整数どうしなので丸め不要
}
```

## 7. 勝ち／負け／引き分けの判定

Phase 3 の分析（勝率など）と一覧の「勝ち/負け/引き分け」絞り込み（analytics 4.2）で使う判定です。実装は `calc.js` の `judgeResult()`（architecture 13.1）。**判定結果は保存せず、表示・集計のたびに `profitJpy` から求めます**。

| 判定 | 条件 |
|---|---|
| 勝ち | `profitJpy > 0` |
| 負け | `profitJpy < 0` |
| 引き分け | `profitJpy === 0`（**損益0円は引き分け**） |
| 判定対象外 | `status = open`（保有中）、`deletedAt` がある（論理削除済み） |

- **判定の基準は損益（円）** です（pips ではありません）。手入力で上書きした値（`profitSource = manual`）も含め、保存されている `profitJpy` を使います。
  - 例：+0.5pips でも、手数料込みの確定損益を −30円で上書きしていれば「負け」。
- 決済理由（`exitReason`）が「建値決済（`breakeven`）」でも、判定は損益（円）で行います（例：建値決済で +50円なら「勝ち」）。
- 勝率を計算するときに引き分けを分母に含めるかどうかは、T-50（分析指標の計算式）で決めます。

## 8. 入力値の妥当性チェック

### 8.1 入力文字の正規化（チェックの前に行う）

- 前後の空白を取り除く
- 全角数字・全角ピリオド（`１５０．２５`）は半角（`150.25`）に直す
- 損益（円）の手入力に限り、カンマ（半角 `,`・全角 `，`）を取り除き、全角のマイナス記号（`−` `－`）を半角 `-` に直し、**先頭の `+`（全角 `＋` も）を1つだけ取り除く**（全角カンマと先頭の `+` は 2026-10-16 オーナー決定・14.2 #6。業者アプリの表示 `+2,480` や全角の `－５，７００` をそのまま写しても入力できるようにするため）
- 上記以外の文字（カンマ区切りの価格 `150,25`、指数表記 `1e2` など）は「数値で入力してください」のエラー
- 桁数は**文字列のまま**数える。小数部の末尾の0は数えない（`150.1200` は小数第2位として扱う）
- **受け付け方の細目（T-13 で確定・architecture 13.3 #3、T-14 で確認済み。2026-10-16 にオーナーが現状どおりで確定・14.2 #7）**：
  - 整数部や小数部を省いた `.5`（＝0.5）・`150.`（＝150）は数値として受け付ける
  - 1lotの通貨数（E-07）のカンマ付き `10,000` はエラー（カンマを取り除くのは損益（円）の手入力だけ）。`10000.0` のように末尾が0だけの小数は整数として受け付ける。画面のエラー文は「カンマなしで」を添えた形にする（design 14.6.2）
  - 損益（円）の手入力（E-09）は、小数点を含む入力は値が整数でも（`1234.0`）エラー
  - 先頭の `+`：価格・ロット・1lotの通貨数・円換算レートでは受け付けない（例 `+150.25` は E-01）。**損益（円）の手入力だけは1つ受け付ける**（`+2,480`・`＋2,480` → 2480。2026-10-16 変更・14.2 #6）。符号が2つ以上（`+-5`・`++5`）や符号だけ（`+`）は E-09

## 10. 通貨ペアマスタ（T-03）

アプリで選べる通貨ペアの一覧と、ペアごとの「pip単位・価格の桁数」を定めます。3章（pips）・4章（損益）・8章（入力チェック）は、ここで決めた値を使って計算・チェックします。

### 10.1 この章で使う用語

| 用語 | 一言説明 |
|---|---|
| 通貨ペアマスタ | アプリに最初から登録しておく通貨ペアの一覧表（マスタ＝基準となる一覧データ）。コード内の定数として持ち、ユーザーの設定には保存しない |
| 表示桁数（`priceDecimals`） | 価格を画面に表示するときの小数の桁数。一般的な業者アプリと同じく **pip の1/10（1ポイント）まで**（JPYペア 第3位、非JPYペア 第5位） |
| 入力桁数上限（`maxInputDecimals`） | 価格として入力できる小数の桁数の上限（8.2 の E-03・E-04）。表示桁数と同じ値 |
| 円換算ペア | 非JPYペアの損益を円にするときに、円換算レート（4.3）として入力するペア。決済通貨/JPY（例：EUR/AUD なら AUD/JPY） |
| 高金利通貨 | 南アフリカランド（ZAR）・メキシコペソ（MXN）・トルコリラ（TRY）など、金利が高めの新興国通貨。価格が数円〜十数円と小さく、日本の個人向け業者でよく扱われる。**オーナーは取引しない**（2026-10-15 決定。10.6） |
| 正規化 | 入力の表記ゆれ（小文字・全角・区切り記号の違い）をそろえて、同じ形（`USD/JPY`）に直すこと |

| 入力桁数上限 | `maxInputDecimals` | number | 3 | 5 | 価格入力の小数桁の上限（E-03・E-04） |
| ポイント倍率 | `pointScale` | number | 1,000 | 100,000 | `10 ^ priceDecimals`。3.3・6.4 の「倍率」と同じ |
| 円換算ペア | `quoteToJpyPair` | string / null | `null` | `USD/JPY` | 4.3 の `quoteToJpyRate` に入れるレートのペア。決済画面の入力欄のラベルに使う（例：「円換算レート（USD/JPY）」） |
| 価格帯の目安 | `warnMin` / `warnMax` | number / null | 50 / 300 | 0.5 / 2.5 | W-06 の警告に使う（10.5、**2026-10-15 採用**）。`null` はチェックしない |

- **常に成り立つ関係**：`priceDecimals = maxInputDecimals`、`pipSize = 10 ÷ pointScale`（1pip ＝ 10ポイント）。この関係があるので、3.3 の `pips = diffPoints ÷ 10` はどのペアでもそのまま使えます。
- 6.4 の参照実装の `isJpyPair(pair)`・`pointScale(pair)` は、T-03 以降 `getPairSpec(pair).isJpyPair`・`getPairSpec(pair).pointScale`（10.7）に置き換えます。下表の19ペアはすべて判定ルール（10.4）と同じ値なので、**9章のテストケースの結果は変わりません**（10.8 P-05 で確認）。

### 10.4 ユーザーが通貨ペアを追加するときの判定ルール

設定画面（よく使う通貨ペア）や「その他」の選択シートで、ユーザーが通貨ペアを入力して追加するときのルールです。追加したペアは `favoritePairs` に加えるだけで、**マスタやその他の設定キーは増やしません**（pip単位などは `pair` の文字列から毎回同じ結果が求まるため）。

**手順1：入力の正規化**

| # | 処理 | 例 |
|---|---|---|
| 1 | 全角を半角に直す（Unicode の NFKC 正規化） | `ＥＵＲ／ＮＺＤ` → `EUR/NZD` |
| 2 | 英小文字を大文字に直す | `usd/sek` → `USD/SEK` |
| 3 | 空白を取り除く | ` sgd / jpy ` → `SGD/JPY` |
| 4 | 区切りは `/`・`-`・`_`・区切りなし（6文字）を受け付け、`/` にそろえる | `EUR-CHF`・`USDSEK` → `EUR/CHF`・`USD/SEK` |

**手順2：チェック（上から順に判定し、最初に当てはまったもので止める）**

| # | 条件 | 結果 | メッセージ例 |
|---|---|---|---|
| E-12 | 正規化後が「英字3文字＋`/`＋英字3文字」でない | エラー | 通貨ペアは「USD/JPY」の形で入力してください |
| E-13 | 基軸・決済のどちらかが貴金属・暗号資産のコード（`XAU` `XAG` `XPT` `XPD` `BTC` `ETH`） | エラー | このアプリはFXの通貨ペアのみ記録できます（Q-05） |
| E-14 | 基軸通貨と決済通貨が同じ（例 `USD/USD`） | エラー | 2つの異なる通貨を入力してください |
| E-15 | 基軸通貨が JPY（例 `JPY/USD`） | エラー | 円が左側の通貨ペアは対象外です（例：USD/JPY の形で入力してください） |
| E-16 | すでに `favoritePairs` にある | エラー | この通貨ペアはすでに登録されています |
| W-07 | マスタにないペアで、基軸・決済のどちらかが「確認済み通貨」（下記）以外 | 警告（確認のうえ追加できる） | このアプリで確認していない通貨です。pips の値が業者の表示と異なる場合があります（損益（円）は手入力で上書きできます） |

- **確認済み通貨**（pip単位の慣習が下のルールと一致することを確認した通貨）：`JPY` `USD` `EUR` `GBP` `AUD` `NZD` `CAD` `CHF` `ZAR` `MXN` `TRY` `CNH` `HKD` `SGD` `SEK` `NOK` `DKK` `PLN`
- マスタにあるペア（例：「その他」から CHF/JPY を選ぶ）は、E-16 以外のチェックに当てはまらないので、そのまま追加されます。

**手順3：pip単位・桁数の決め方**

| 決済通貨（`quote`） | `pipSize` | `priceDecimals` / `maxInputDecimals` | `pointScale` | 例 |
|---|---|---|---|---|
| `JPY` | 0.01 | 3 | 1,000 | SGD/JPY、HKD/JPY |
| `JPY` 以外 | 0.0001 | 5 | 100,000 | USD/SEK、EUR/NZD |

- マスタにあるペアは**マスタの値を優先**します（現在の19ペアはすべてこのルールと同じ値）。このルールに合わないペアを将来マスタに入れる場合は、10.7 の例外表 `PIP_EXCEPTIONS` に個別に書きます（現時点では空）。
- 決済通貨の1単位の価値が小さい通貨（例：ハンガリーフォリント `HUF`。USD/HUF は数百の値になる）では、業者が 0.01 を 1pip とすることがあり、このルールだと **pips の値が業者の表示と100倍ずれる**可能性があります（そのため W-07 で知らせます）。ただし**損益（円）の計算は pip単位に関係なく正しく求まります**（値幅 × 数量 × 円換算レートで計算するため。5桁まで入力できれば価格もそのまま入れられます）。
  - 注意（T-14 で追記）：円換算レートは小数第3位まで（E-08）なので、決済通貨の円レートがとても小さい通貨（例：HUF/JPY は 0.4 前後、インドネシアルピア IDR/JPY は 0.01 未満）では、レートの丸めにより自動計算値が業者の値と数%ずれることがあります。HUF/JPY（0.412 など）では約0.1%以内ですが、IDR のように 0.01 を下回る通貨では誤差が大きくなるため、損益（円）は業者の確定値で上書きしてください（4.4）。確認済み通貨（上記18通貨）は2026年時点でいずれも円レートが 1 以上で、この問題はほぼありません（最も小さい TRY/JPY でもレートの丸めによるずれは約0.02%以内）。
- **一度公開した判定ルール・マスタの pip単位は変えない**こと。pips は保存済みでも、編集時の再計算（4.5）で過去の記録の pips が変わってしまうためです。どうしても変える場合は、データ移行の扱いを pm・engineer と決めます。
- `favoritePairs` から外したペアの過去の記録も、`pair` の文字列から計算できるので、表示・計算に影響しません。

### 10.5 価格帯の目安による打ち間違い警告（W-06・2026-10-15 採用）

8.3 の W-02（エントリーと決済の差が10%以上）は「2つの価格の差」しか見ないため、**最初に入れるエントリー価格そのものの打ち間違い**（例：USD/JPY を選んだまま EUR/USD の価格 `1.0850` を入れる、`150.12` を `1501.2` と打つ）は見つけられません。そこで、マスタの各ペアに**とても広めの価格帯**を持たせ、外れたら警告します（オーナー決定により採用。警告のみで保存は止めない）。

| 項目 | 内容 |
|---|---|
| 対象 | エントリー価格・決済価格・SL・TP（マスタにあり `warnMin`/`warnMax` が `null` でないペアのみ） |
| 条件 | `価格 < warnMin` または `価格 > warnMax` |
| 結果 | **警告（保存できる）**。メッセージ例「USD/JPY の価格としては大きく外れています。通貨ペアと桁をご確認ください」 |
| 価格帯の決め方 | 過去およそ20年の値動きの範囲の「最安値の約半分〜最高値の約2倍」を、切りのよい数字に丸めたもの。目的は桁違い・ペア違いの検出なので、相場の変動で引っかからないよう**意図的に広く**取っています |
| チェックしないペア | TRY/JPY（長期的に大きく下落してきた通貨で、固定の範囲を決めにくいため）、ユーザーが追加したペア |
| 見直し | 範囲は目安です。正しい価格で警告が出るようになったら（例：数年後）値を広げます |

- 採用の理由：JPYペア（数円〜数百円）と USD建てのペア（1前後）は価格の桁が大きく違うため、この範囲で「ペアの選び間違い」をほぼ確実に検出できます。範囲の数値は相場の歴史に基づく目安なので、上の「見直し」のとおり将来広げることがあります（14章 #6）。
- 画面での表示場所と文言は `docs/design.md` 14.1.8（エントリー価格・SL・TP）・14.2.9（決済価格）に従います。

### 10.6 業者により異なる点・注意

| 項目 | 内容 | アプリでの扱い |
|---|---|---|
| 価格の表示桁数 | 多くの業者は pip の1/10まで（JPYペア 第3位、非JPYペア 第5位）表示するが、それより少ない桁しか表示しない業者もある | 入力は上限以内なら何桁でもよい。表示はマスタの `priceDecimals` まで0で埋める（例：`150.1` → `150.100`） |
| 高金利通貨の1lotの通貨数 | ZAR/JPY・MXN/JPY・TRY/JPY などは、**同じ業者でもペアによって1lotの通貨数が違う**ことがある（例：通常は1lot＝1万通貨でも、これらは1lot＝10万通貨など） | **対象外（2026-10-15 オーナー決定：高金利通貨は取引しない）**。`lotUnitSize` はデモ/本番ごとに1つのまま、ペア別の1lot設定は作らない。マスタには候補として残すがプリセットには含めない（10.3）。万一記録する場合は「ロット欄に1万通貨換算のロットを入れる」か「損益（円）を業者の確定値で上書き」する |
| 例外的な pip単位 | 一部の通貨（HUF など）で、業者により pip の定義が異なる | 10.4 のとおり。損益（円）は正しく計算される |
| 取り扱いペア | 業者ごとに扱うペアが違う | マスタは選択肢の候補。扱いのないペアは選ばなければよい |

### 10.7 参照実装（JavaScript）

engineer はこの関数と**同じ結果**になれば書き方は自由です。

- 実装での置き場所（`docs/architecture.md` 4.2 で確定）：`PAIR_MASTER`・`PIP_EXCEPTIONS`・`KNOWN_CURRENCIES`・`NON_FX_CODES`・`derivePairSpec`・`getPairSpec` は `js/master.js`、`normalizePairInput`・`isOutOfPriceRange` は `js/validate.js`、`formatPrice` は `js/format.js`。6.4 の計算関数（`js/calc.js`）は `isJpyPair(pair)`・`pointScale(pair)` の代わりに `getPairSpec(pair)` を使います。

  { pair: 'EUR/AUD', nameJa: 'ユーロ/豪ドル', warnMin: 0.7, warnMax: 3.5 },
  { pair: 'GBP/AUD', nameJa: 'ポンド/豪ドル', warnMin: 0.9, warnMax: 4 },
  { pair: 'NZD/JPY', nameJa: 'NZドル/円', warnMin: 25, warnMax: 180 },
  { pair: 'CAD/JPY', nameJa: 'カナダドル/円', warnMin: 35, warnMax: 220 },
  { pair: 'CHF/JPY', nameJa: 'スイスフラン/円', warnMin: 40, warnMax: 400 },
  { pair: 'ZAR/JPY', nameJa: '南アフリカランド/円', warnMin: 2, warnMax: 30 },
  { pair: 'MXN/JPY', nameJa: 'メキシコペソ/円', warnMin: 2, warnMax: 25 },
  { pair: 'TRY/JPY', nameJa: 'トルコリラ/円', warnMin: null, warnMax: null },

// 判定ルールと異なる pip単位を使うペアの例外表（現時点では空）
// 例：{ 'USD/XXX': { pipSize: 0.01, priceDecimals: 3, maxInputDecimals: 3, pointScale: 1000 } }
const PIP_EXCEPTIONS = {};
// pip単位の慣習を確認済みの通貨（W-07 の判定に使う）
const KNOWN_CURRENCIES = ['JPY', 'USD', 'EUR', 'GBP', 'AUD', 'NZD', 'CAD', 'CHF', 'ZAR',
  'MXN', 'TRY', 'CNH', 'HKD', 'SGD', 'SEK', 'NOK', 'DKK', 'PLN'];
// FX以外（貴金属・暗号資産）のコード（E-13）
const NON_FX_CODES = ['XAU', 'XAG', 'XPT', 'XPD', 'BTC', 'ETH'];

// 判定ルール（10.4 手順3）で pip単位・桁数を求める
function derivePairSpec(pair) {
  const [base, quote] = pair.split('/');
  const isJpyPair = quote === 'JPY';
  const priceDecimals = isJpyPair ? 3 : 5;
  return {
    pair, base, quote, isJpyPair,
    pipSize: isJpyPair ? 0.01 : 0.0001,
    priceDecimals,
    maxInputDecimals: priceDecimals,
    pointScale: 10 ** priceDecimals,
    quoteToJpyPair: isJpyPair ? null : `${quote}/JPY`,
  };
}

// 通貨ペアの仕様を返す（例外表 → 判定ルールの順。マスタからは名前と価格帯を取る）
function getPairSpec(pair) {
  const m = PAIR_MASTER.find((p) => p.pair === pair);
  return {
    ...derivePairSpec(pair),
    ...(PIP_EXCEPTIONS[pair] || {}),
    nameJa: m ? m.nameJa : pair,
    warnMin: m ? m.warnMin : null,
    warnMax: m ? m.warnMax : null,
    inMaster: Boolean(m),
  };
}

// 通貨ペアの追加入力をチェックする（10.4 手順1・2）
function normalizePairInput(input, favoritePairs) {
  const s = String(input).normalize('NFKC').toUpperCase().replace(/\s+/g, '');
  const m = s.match(/^([A-Z]{3})[\/\-_]?([A-Z]{3})$/);
  if (!m) return { ok: false, error: 'E-12' };
  const [, base, quote] = m;
  const pair = `${base}/${quote}`;
  if (NON_FX_CODES.includes(base) || NON_FX_CODES.includes(quote)) return { ok: false, pair, error: 'E-13' };
  if (base === quote) return { ok: false, pair, error: 'E-14' };
  if (base === 'JPY') return { ok: false, pair, error: 'E-15' };
  if (favoritePairs.includes(pair)) return { ok: false, pair, error: 'E-16' };
  const inMaster = PAIR_MASTER.some((p) => p.pair === pair);
  const warn = !inMaster && !(KNOWN_CURRENCIES.includes(base) && KNOWN_CURRENCIES.includes(quote)) ? ['W-07'] : [];
  return { ok: true, pair, warn, spec: getPairSpec(pair) };
}

// 価格をマスタの表示桁数で表示する（ポイント＝整数を経由して誤差なく0埋め）
function formatPrice(price, pair) {
  const { pointScale, priceDecimals } = getPairSpec(pair);
  const pts = Math.round(price * pointScale); // 入力桁数が上限以内なら正確な整数
  const digits = String(Math.abs(pts)).padStart(priceDecimals + 1, '0');
  return (pts < 0 ? '-' : '') + digits.slice(0, -priceDecimals) + '.' + digits.slice(-priceDecimals);
}

// W-06：価格帯の目安から外れているか（10.5。2026-10-15 採用）
function isOutOfPriceRange(price, pair) {
  const { warnMin, warnMax } = getPairSpec(pair);
  if (warnMin == null || warnMax == null) return false;
  return price < warnMin || price > warnMax;
}

## 11. セッション判定時刻（T-03）

エントリー日時（`entryAt`）から `session`（`tokyo` / `london` / `newyork` / `other`）を自動で決めるルールです（requirements.md 6.1、Q-07）。判定結果は初期値で、ユーザーは画面で変更できます。

### 11.1 この章で使う用語

| 用語 | 一言説明 |
|---|---|
| セッション | 世界の主な為替市場（東京・ロンドン・ニューヨーク）が開いていて、取引の中心になっている時間帯。FX は平日ほぼ24時間取引できるが、時間帯で値動きの性質が変わるため、振り返りの切り口として使う |
| 夏時間（DST） | Daylight Saving Time。夏の間だけ時計を1時間進める制度。米国・英国（欧州）にはあり、**日本にはない**。そのため日本時間で見ると、夏は海外市場が1時間早く始まる |
| 標準時（冬時間） | 夏時間でない期間の時刻。NY は UTC−5、ロンドンは UTC±0 |
| UTC | 協定世界時。世界共通の基準時刻。日本時間（JST）は UTC＋9時間 |
| 現地時刻 | その市場がある都市の時計の時刻（ロンドン時刻、NY時刻） |
| NYクローズ | NY時刻の17:00。FX業界で「1日の区切り」として広く使われる時刻（日足の切り替えやスワップの付与の基準になることが多い） |
| ずれ期間 | 米国と欧州で夏時間の開始日・終了日が違うために、**米国だけが夏時間**になっている期間（3月の2〜3週間と、10月末〜11月初めの1週間） |
| IANAタイムゾーン | `America/New_York`・`Europe/London`・`Asia/Tokyo` のような地域名。ブラウザが内蔵する世界の時差・夏時間のデータベースで、これを指定すると夏時間を自動で反映した現地時刻が得られる |

### 11.2 採用するセッションの定義

各市場の始まりを**その市場の現地時刻**で決めます。現地時刻で決めておけば、夏時間による日本時間のずれは自動的に反映されます。

| `session` | 画面表示 | 始まり | 終わり | 日本時間（冬） | 日本時間（夏） |
|---|---|---|---|---|---|
| `tokyo` | 東京 | 日本時間 9:00 | ロンドンの始まり | 9:00〜17:00 | 9:00〜16:00 |
| `london` | ロンドン | ロンドン時刻 8:00 | NYの始まり | 17:00〜22:00 | 16:00〜21:00 |
| `newyork` | NY | NY時刻 8:00 | NYクローズ（NY時刻 17:00） | 22:00〜翌7:00 | 21:00〜翌6:00 |
| `other` | その他 | NYクローズ | 日本時間 9:00 | 7:00〜9:00 | 6:00〜9:00 |

- `other` は平日の早朝（オセアニア時間とも呼ばれ、ウェリントン・シドニー市場が中心の時間帯）と、土日（11.5）です。
- 「画面表示」の「NY」は入力画面のセグメント（幅が狭い）での表示です。詳細画面では略さず「ニューヨーク」と表示します（design 14.1.4・14.4.4）。
- 時刻の範囲は**始まりを含み、終わりを含まない**（例：夏の 16:00:00 ちょうどは `london`、15:59:59 は `tokyo`）。秒は切り捨てて分単位で判定します。

### 11.3 夏時間のルール

| 地域 | 夏時間の開始 | 夏時間の終了 | 日本時間で見た切り替えの瞬間 | 根拠 |
|---|---|---|---|---|
| 米国（NY） | **3月の第2日曜** 現地2:00 | **11月の第1日曜** 現地2:00 | 開始：日曜 16:00 / 終了：日曜 15:00 | 2007年以降の米国の制度 |
| 英国・EU（ロンドン） | **3月の最終日曜** UTC 1:00 | **10月の最終日曜** UTC 1:00 | 開始・終了とも日曜 10:00 | EU・英国の制度（英国はEU離脱後も同じ日程） |

- 米国は欧州より**2〜3週間早く始まり、1週間遅く終わる**ため、その間が「ずれ期間」（米国だけ夏時間）になります。逆（欧州だけ夏時間）になる期間はありません。
- 切り替えは**どれも日曜日（市場が閉まっている間）に起きる**ため、実際の判定では「月曜から新しい時刻表に切り替わる」と考えて構いません。
- 各国の制度が変わった場合（例：米国で夏時間を廃止・通年化する法改正）は、ブラウザのタイムゾーンデータが更新されれば 11.7 の参照実装は自動で追従します（11.4 の表と 11.8 の期待値は見直しが必要）。

| ① 冬（米欧とも標準時） | 11月第1日曜〜3月第2日曜（2026/11/1〜2027/3/14） | 9:00〜17:00 | 17:00〜22:00 | 22:00〜翌7:00 | 7:00〜9:00 |

### 11.5 重なる時間帯の優先・土日・祝日の扱い

| 場面 | ルール | 理由 |
|---|---|---|
| ロンドンとNYが両方開いている時間（例：夏の 21:00〜翌1:00 ごろ） | **`newyork` を優先**（あとから始まる市場に引き継ぐ） | NY の始まりの時間帯には米国の主要な経済指標の発表（NY時刻 8:30＝日本時間 21:30／22:30）が集中し、値動きの性質が変わる区切りとして分かりやすいため |
| 東京とロンドンが両方開いている時間（例：冬の 17:00 前後） | **`london` を優先**（同上） | 同上の考え方で統一。欧州勢の参入で値動きが変わる区切りとして使われることが多いため |
| 東京のお昼〜ロンドンの始まりの前（例：冬の 15:00〜17:00） | `tokyo` のまま | 午後に `other` の空白を作らず、`other` を「早朝・週末」だけにして意味を分かりやすくするため |
| 土曜の 0:00〜NYクローズ（冬 7:00／夏 6:00） | `newyork` | 金曜のNYセッションの続き（NY時刻ではまだ金曜） |
| 土曜のNYクローズ以降〜月曜 9:00 | `other` | 為替市場が閉まっている（週末）。月曜の早朝は平日と同じく `other` |
| 祝日・年末年始・クリスマスなど | **考慮しない**（平日と同じ時刻で判定） | 休場日は国・業者で異なり、毎年変わるため。必要ならユーザーが手動で変更する |

- **重なる時間帯の情報は失われます**（`newyork` と記録された中に、ロンドンとの重なりの時間が含まれる）。より細かく振り返りたい場合は、分析画面の「時間帯別」（エントリー日時の時刻で集計、F-06）を併用します。重なり専用の値（例：`overlap`）は **enum に追加しない**ことに決まりました（14章 #8、2026-10-15 決定）。

### 11.6 判定時刻に諸説あることと、採用した根拠

セッションの時間帯には**公式な定義がなく、業者・解説サイト・ツールにより異なります**。代表的な違いは次のとおりです。

| 市場 | よく見かける定義（日本時間、冬／夏） | 本アプリの採用 |
|---|---|---|
| 東京 | 開始 8:00 または 9:00、終了 15:00・17:00 など | 9:00〜ロンドンの始まり |
| ロンドン | 開始 17:00／16:00（現地 8:00）、終了 翌2:00／翌1:00（現地 17:00）など | 現地 8:00〜NYの始まり |
| NY | 開始 22:00／21:00（現地 8:00）、または 23:30／22:30（株式市場の開始 現地 9:30）、終了 翌7:00／翌6:00（現地 17:00） | 現地 8:00〜現地 17:00 |
| 重なり | 「ロンドン・NY重複時間」を別扱いにすることも多い | NY を優先（11.5） |

**採用した根拠**

1. **現地時刻で定義する**：夏時間の切り替え日を米欧それぞれ正しく反映でき、ずれ期間も自動で扱える。ブラウザのタイムゾーン機能（11.7）で、夏時間の表を自前で持たずに実装できる。
2. **ロンドン・NY の開始を現地 8:00 とする**：日本の解説で最も多く見られる「ロンドン 16時／17時、NY 21時／22時」と一致する。
3. **NY の終了を現地 17:00（NYクローズ）とする**：FX業界で1日の区切りとして広く使われ、日足の切り替えと一致することが多い。
4. **東京の開始を 9:00 とする**：東京の銀行間取引が本格化し、9:55 の仲値（銀行が当日の顧客向けレートを決める時刻）に向けて取引が増える時間帯。8:00 開始とする定義もあるが、早朝はオセアニア時間として `other` にまとめた。
5. **重ならないように区切る（あとから始まる市場を優先）**：`session` は1つの値しか持てない（enum）ため、1つの日時に必ず1つのセッションが決まる必要がある。

> この定義は「振り返りの切り口として一貫した区切りを付ける」ためのもので、どの時間帯に取引すべきかを示すものではありません。

### 11.7 判定アルゴリズムと参照実装

**判定手順**（上から順に判定し、最初に当てはまったもので決める）

| 順 | 条件（現地時刻で判定） | 結果 |
|---|---|---|
| 0 | 日時として読めない（`null`・`undefined`・空文字を含む） | `null`（セッション未設定。保存は止めない） |
| 1 | NY時刻で「金曜 17:00 以降」「土曜」「日曜 17:00 より前」のいずれか | `other`（週末） |
| 2 | NY時刻が 8:00〜17:00 | `newyork` |
| 3 | ロンドン時刻が 8:00 以降、かつ NY時刻が 8:00 より前 | `london` |
| 4 | 日本時刻が 9:00 以降、かつ ロンドン時刻が 8:00 より前 | `tokyo` |
| 5 | 上記以外（平日の NYクローズ〜日本時刻 9:00） | `other` |

- 現地時刻は、ブラウザ標準の `Intl.DateTimeFormat` に IANAタイムゾーン（`America/New_York`・`Europe/London`・`Asia/Tokyo`）を指定して求めます。**端末のタイムゾーン設定に関係なく**同じ結果になります（海外旅行中に記録しても日本時間基準で判定）。
- `entryAt` は requirements.md 6.1 のとおりタイムゾーン付きの文字列（例 `2026-10-15T21:30:00+09:00`）。`+09:00` 以外（`Z` など）で表されていても、同じ瞬間なら同じ結果になります。
  - **タイムゾーンのない文字列（`datetime-local` の値 `2026-10-15T21:30` など）をそのまま渡さない**こと（T-14 で追記）。JavaScript はこれを端末のタイムゾーンの時刻として読むため、海外の端末では判定が変わります。architecture 6.6 の形式に直してから渡します。
  - `null` は JavaScript の `new Date(null)` が1970年1月1日として読めてしまうため、判定の最初に `null` を返す（T-14 で参照実装を訂正。それまでの版では `'tokyo'` が返っていた）。
- 対象ブラウザ（iOS Safari 16.4以降・Android Chrome）はいずれも `Intl.DateTimeFormat` のタイムゾーン指定に対応しています。万一例外が発生した場合は `null` を返し、保存は止めません。
- 時刻の取り出しには `hourCycle: 'h23'` を指定します（`hour12: false` だと一部の環境で 0時が「24」と表示されることがあるため）。

**再判定のタイミング**

| 場面 | 扱い |
|---|---|
| エントリー画面を開いたとき・エントリー日時を変えたとき | 自動判定し、セッション欄に初期値として表示 |
| ユーザーがセッションを手動で選んだ後に、エントリー日時を変えたとき | **手動の選択を優先して上書きしない**。判定方法：変更前の日時での判定結果と現在の `session` が同じなら自動のまま（新しい日時で再判定）、違えば手動で変えたものとみなしてそのまま残す（判定元を記録する新しいキーは作らない） |
| 判定ルールを将来変更したとき | 保存済みの記録は再判定しない（`session` は保存値を正とする） |

```js
// 指定したタイムゾーンでの曜日（0=日〜6=土）と、0時からの経過分を返す
const tzFormatters = {};
function localParts(date, timeZone) {
  const f = tzFormatters[timeZone] || (tzFormatters[timeZone] = new Intl.DateTimeFormat('en-US', {
    timeZone, weekday: 'short', hour: '2-digit', minute: '2-digit', hourCycle: 'h23',
  }));
  const p = {};
  for (const { type, value } of f.formatToParts(date)) p[type] = value;
  return {
    wd: ['Sun', 'Mon', 'Tue', 'Wed', 'Thu', 'Fri', 'Sat'].indexOf(p.weekday),
    min: Number(p.hour) * 60 + Number(p.minute), // 秒は切り捨て
  };
}

// セッション判定（11.7 の判定手順 0〜5）
function judgeSession(entryAt) {
  if (entryAt == null) return null; // new Date(null) は 1970-01-01 になってしまうため（T-14 で追加）
  const d = entryAt instanceof Date ? entryAt : new Date(entryAt);
  if (Number.isNaN(d.getTime())) return null;
  try {
    const H = (h) => h * 60;
    const ny = localParts(d, 'America/New_York');
    const ldn = localParts(d, 'Europe/London');
    const jp = localParts(d, 'Asia/Tokyo');
    // 1. 週末：NY時刻の金曜17:00〜日曜17:00は市場休止
    if ((ny.wd === 5 && ny.min >= H(17)) || ny.wd === 6 || (ny.wd === 0 && ny.min < H(17))) return 'other';
    // 2. NY：NY時刻 8:00〜17:00
    if (ny.min >= H(8) && ny.min < H(17)) return 'newyork';
    // 3. ロンドン：ロンドン時刻 8:00〜（NYの始まりまで）
    if (ldn.min >= H(8) && ny.min < H(8)) return 'london';
    // 4. 東京：日本時刻 9:00〜（ロンドンの始まりまで）
    if (jp.min >= H(9) && ldn.min < H(8)) return 'tokyo';
    // 5. それ以外（平日の早朝）
    return 'other';
  } catch (e) {
    return null;
  }
}
```
