### SS-R01（低）送信が失敗したとき、その送信の最中に保存した記録まで「送る列」から捨てられる（T-42 までは、その記録をもう一度変えるまで送られない）
- 該当：js/sync-sender.js:202-208（drain：sendBatch が false を返すと `queue.clear()`）、js/sync-sender.js:172-173（送る分は送信前に列から外している）
- 何が起きるか（本物の trades.js・sync-sender.js をメモリの DB で動かして確認）：記録 1 の送信が Apps Script の応答待ちの間に記録 2・3 を保存し、記録 1 の応答が BUSY（または時間切れ・届かない）になると、記録 2・3 は一度も送られずに列から消える（3件とも `pending`、Apps Script に届いた要求は 0）。設定の問題で止めたときは、どのみち送らないので問題ないが、一時的な失敗では「たまたまその時間に保存した記録」が取り残される。記録の中身は端末に残っており、消える・壊れることはない。
- T-41 だけを公開した状態では、送り直し（起動時・オンライン復帰時・「今すぐ同期」）が無いので、その記録は**次にその記録を変えるまでシートに入らない**。同期の状態の画面（T-43）もまだ無いので、オーナーは気づけない。オフライン中に保存した記録・送る前にアプリを閉じた記録・T-41 より前からある記録も同じく、T-42 まで送られない（これは仕様どおり）。
- 修正案：一時的な失敗で止めるときは、失敗した回の id だけを捨て、送信中に足された id は列に残す（次のきっかけで送る）。あるいは T-42 の再送（起動時・`online`・前面に戻ったとき）をこのまま入れれば実害は無くなるので、T-41 単独で長く公開しない。公開する場合は「T-42 までは、送れなかった記録はその記録を次に変えたときに送られる」ことをオーナーに伝えておく。

### SS-R02（低）接続テストが成功しても、設定の問題で止めた自動送信は再開しない（アプリを完全に閉じて開き直すまで）
- 該当：js/sync-sender.js:164-167（blockedKey は URL・合言葉の組が変わったときと requestUnsent({ manual: true }) でしか解けない）、js/screens/settings-sync.js:212（接続テストは pingAppsScript を直接呼び、送信のしくみに結果を伝えない）
- 何が起きるか：シートの見出し違い（HEADER_MISMATCH）・Apps Script 側の合言葉の未設定（TOKEN_NOT_SET）・Sheets API の追加忘れ（INTERNAL＋SHEETS_API_NOT_ADDED）などで止まったあと、オーナーがシート／Apps Script 側を直し、アプリの設定画面で接続テストを押して「接続できました」と出ても、URL・合言葉が同じなので自動送信は止まったまま。iPhone のホーム画面版はアプリを切り替えても裏で生きていることが多く、「開き直す」のは利用者には分かりにくい。T-41 の時点では「今すぐ同期」（T-42）も同期状態の画面（T-43）も無いので、止まっていることにも気づけない。データは端末に残る（pending のまま）ので消失ではない。
- 修正案：接続テストが `ok` だったら、その URL・合言葉での停止を解く（例：sync-sender に `clearBlock()` を足し、settings-sync の runTest の成功時に呼ぶ。または接続テストの成功で `requestUnsent({ manual: true })` 相当を呼ぶ）。T-42 の「今すぐ同期」・T-43 の画面と合わせて決めてもよい。

### SS-R03（低）「受け付けられなかった記録」の知らせ（syncLastError の rejected と id）が、そのあとの一時的な失敗で上書きされ、次の成功で消える
- 該当：js/sync-sender.js:128-130（recordFailure は前のエラーを見ずに上書き）、js/sync-sender.js:138-155（afterSuccess は前のエラーが rejected のときだけ id を残す）
- 何が起きるか（模擬 Apps Script〔本物の gas/Code.gs〕で確認）：日時の形が違う記録を送る → `{kind:'rejected', reason:'BAD_DATETIME', ids:[…]}`、記録は `error`。続けてオフラインで別の記録を保存 → `{kind:'offline'}` に上書き。オンラインで次の保存が成功 → `null`。記録は `error` のまま残るが、**どの記録が・なぜ受け付けられなかったか**（sheets-setup 9.1 の「受け付けなかった記録の件数と ID」）は残らない。T-43 は `syncStatus = error` の件数は数えられるが、理由のコードは失われる。ふつうはアプリの誤りでしか起きない（11.5）ので頻度は低い。
- 修正案：rejected の情報（reason・ids）は、ほかの種類のエラーで上書きするときも別の欄（例 `rejected: { reason, count, ids }`）として持ち越す。または T-43 で「`error` の記録があるのに syncLastError が rejected でない」場合の表示を決めておく。

### SS-R04（低・要確認）CSV の取り込みなどで多くの記録を続けて送ると、Google Sheets API の「1分あたりの書き込み回数」の上限に当たるおそれがある
- 該当：js/sync-sender.js:202-208（20件ずつ、間を空けずに続けて送る）、gas/Code.gs:507-518（writeRow_：方式 C は1行ごとに `Sheets.Spreadsheets.Values.update` を1回呼ぶ）
- 何が起きるか（推測。本物では未確認）：Sheets API の書き込みには「1ユーザー・1プロジェクトあたり1分60回」程度の上限がある（Google の公開している既定値）。1回の要求で20回書くので、要求が20秒より速く返ると1分に3回を超えて上限に当たり、Apps Script の中で例外 → `INTERNAL`（一時的な失敗）になる。すると送信はそこで止まり（SS-R01 のとおり残りは列から捨てられる）、一部の行だけシートに入った状態になる。行が二重になる・記録が壊れることはない（送り直せば `id` で上書き）。
- 修正案：まず本物で 100件程度の取り込みを送って確かめる（T-42・T-48）。当たるなら、Apps Script 側で1回の要求の値を `Sheets.Spreadsheets.Values.batchUpdate` 1回にまとめる（表示形式の設定は今のまま行ごと）か、アプリ側で `INTERNAL` のあとに少し待って続きを送る（T-42 の再送の間隔と一緒に決める）。
