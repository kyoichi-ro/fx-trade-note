## 指摘一覧

### RS-R01（低）1分あたりの上限（40件）の待ちを「送る直前の読み直し」より前に数えるため、すでに synced の id のために最大1分待つ（その間の新しい保存・「今すぐ同期」も待たされる）
- 該当：js/sync-sender.js:313-314（sendBatch の最初に `waitForBudget(Math.min(perBatch, queue.size))`）、js/sync-sender.js:326-329（synced を除くのはそのあと）、js/sync-sender.js:429-449（requestUnsent は送信中の回の id も列に足し直す）
- 何が起きるか（本物の trades.js・sync-sender.js＋本物の gas/Code.gs、仮想時計で確認）：未送信35件で起動 → 2秒後に20件を送信中に「今すぐ同期」（または online の再送）が来ると、送信中の20件の id も列の後ろに足される。2回目に残り15件を送ったあと、列には synced になった20件分の id だけが残り、`waitForBudget(15)` が「直前1分 35件＋15件＝50件 > 40件」と数えて **約56秒待つ**。待ったあと読み直すと全部 synced で何も送らない。その間（10秒の時点）に保存した新しい記録は、実際の件数は36件で上限内なのに **62秒の時点まで送られない**。syncNow() も 6秒で済むところが 64秒かかる（T-43 のボタンの「同期中」が1分続く）。行の重複・記録の変化は無い。未送信21件では起きない（待ちが要らない）。
- 修正案：待つ件数を「読み直して synced を除いたあとの件数」で数える（loadTrades → 絞り込み → `waitForBudget(trades.length)` → 待ったなら読み直す）。または送信中の回の id を覚えておき、request() で足し直さない。テストに「上限に近いとき、synced の id だけが列に残っていても待たない」を足す。

### RS-R02（低）受け付けられなかった記録が11件以上あると、id の分かる10件が直った時点で、残りが error のままでも知らせ（syncLastError）が消える
- 該当：js/sync-sender.js:246-250（keptCount は件数で数えている）、js/sync-sender.js:258-263（残す条件が `kept.length > 0`＝id の分かる記録が残っているときだけ）
- 何が起きるか（模擬環境で確認）：日時の形が違う12件を送る → `{ kind: 'rejected', count: 12, ids: 10件 }`。id の分かる10件を直して保存 → 10件は synced になり、**syncLastError は null**。残りの2件は `error` のまま（`synced 10 / error 2`）。SS-R03 で「記録が受け付けられる〔synced になる〕まで消さない」とした約束が、11件以上のときだけ守られない。T-43 は `syncStatus＝error` の件数は数えられるが、理由のコード（BAD_DATETIME など）は失われる。ふつうはアプリの誤りでしか起きない（sheets-setup 11.5）ので頻度は低い。
- 修正案：`keptCount > 0` のあいだは `kind: 'rejected'`（ids は空でもよい・count は keptCount）で残す。または、知らせを消す前に DB の `syncStatus＝error` が0件かを確かめる。テストに「12件中10件が直ったとき」を足す。

### RS-R03（低・まれ）端末の時計が戻ると、1分の上限の待ちが「戻った時間＋1分」になり、その間は保存しても送られない
- 該当：js/sync-sender.js:289-302（sentInLastMinute・waitForBudget は `Date.now()` の差で数える。差が負なら古い分が外れず、待ち時間 `sentLog[0].at + 60秒 − 今` が長くなる）、js/sync-sender.js:179（nowMs の既定が `Date.now()`）
- 何が起きるか（仮想時計で確認）：40件を送った直後に端末の時計が1時間戻る → 次の保存で「3659秒待ってから続きを送ります」と出て、**約61分、送信が止まる**（running のままなので、そのあとの保存・「今すぐ同期」もすべて後ろに並ぶ）。アプリを完全に閉じて開き直せば直る。記録は pending のまま残り、消える・壊れることはない。iPhone は時刻を自動で合わせるのがふつうで、手で時計を戻したときくらいしか起きない（自動の補正の数秒なら、待ちが数秒のびるだけ）。前面に戻ったときの間隔（lastSendAt）も同じく、戻った時間のあいだ働かない。
- 修正案：1回の待ちを最大60秒に抑え、`at` が今より未来の記録は捨てる（時計が戻ったとみなす）。または nowMs の既定を単調に増える `performance.now()` にする（送る時刻・エラーの時刻の now は今のまま `nowJst`）。

### RS-R04（低・要確認）1回分（20件）の送信が本物の Google でいつも60秒を超えると、同じ20件を送り続けて synced にならず、新しく保存した記録もその後ろで止まる
- 該当：js/sync-sender.js:346-349（時間切れも一時的な失敗として、同じ回の id を列の先頭に戻す）、js/sync-sender.js:326（次も先頭から同じ20件）、js/sync.js:65（UPSERT_TIMEOUT_MS＝60秒）・72（SYNC_BATCH_SIZE＝20）
- 何が起きるか（模擬環境で、20件の要求だけ応答が時間切れより遅くなるようにして確認）：Apps Script は20行を書き終えているのに、アプリは timeout → 列の先頭に戻す → 30秒・2分・10分後と、前面に戻るたび（1分に1回まで）に**同じ20件をまた送り**、毎回時間切れになる。10回送ってもシートは20行（重複なし）だが、記録は20件とも `pending` のまま。新しく保存した記録は列の後ろに足されるので、先頭の20件が通るまで**送られない**（1件ずつの保存なら数秒で済むはずのものも止まる）。止まっていることは T-43 まで画面では分からない。記録が消える・壊れる・行が二重になることは無い。T-41 のレビューでも「20件で60秒に収まるか」は未確認のまま（方式 C は1行ごとに `SpreadsheetApp.flush()` と Sheets API の書き込みを1回ずつ行う）。push すると、オーナーの iPhone に溜まっている未送信が20件ずつ送られ始めるので、最初に当たる場面になる。
- 修正案：まず本物で「20件の要求にかかる時間」を測る（T-48 を待たず、push の直後にオーナーに設定画面の同期状態か Apps Script の「実行数」で確かめてもらう、など）。コード側では、時間切れのあとは1回の件数を半分ずつ減らす（20 → 10 → 5 → 1。成功したら戻す）か、時間切れのあとの再送では、その回の id より「あとから保存された記録」を先に送る。

### RS-R06（低）溜まった未送信をまとめて送っている間に保存した記録は、溜まっていた分をすべて送り終えるまで送られない（1分40件なので、100件溜まっていれば約2分半）
- 該当：js/sync-sender.js:413-417（request は列の後ろに足す）、js/sync-sender.js:117-122・583-588（未送信は作った順）、js/sync-sender.js:295-303（1分40件）
- 何が起きるか（模擬環境・仮想時計で確認）：1000件の未送信を送っている途中（1分目）に保存した記録は、**25分目**に送られた。開き直すと、作った順に並べ直すので、新しい記録はまた最後になる。push の直後は、オーナーの iPhone に溜まっている未送信（T-41 より前の記録・オフライン中の記録など）が先に送られるので、その件数 ÷ 40 分ほど、新しく保存した記録がシートに出ない（「保存すると数秒でシートに1行増える」という T-41 で確かめた動きと違って見える）。記録・行には影響しない。
