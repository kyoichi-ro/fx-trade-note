## 指摘一覧

### R-01（低）極端に大きい価格・ロットで計算が例外／Infinity になる
- 該当：js/validate.js:87-96（parsePrice に上限なし）、js/validate.js:102-109（parseLots に上限なし）、js/calc.js:129（BigInt(diffPoints)）
- 何が起きるか（Node で実行して確認）：
  - 価格に 307 桁以上の数字（1e306 など）を貼り付けると、parsePrice は ok で通り、toPoints が Infinity → calcProfitJpy が `RangeError: The number -Infinity cannot be converted to a BigInt` を投げる。エントリーは W-06（警告）だけで保存できるため、その記録の決済画面・編集画面では入力のたびに evaluateClose → computeClose が例外になり、画面の再描画が止まる。
  - ロットに巨大な値（1e306）を入れると W-04（警告）だけで保存でき、決済時の profitJpy が `Infinity` になって保存される（CSV では空欄、集計は Infinity）。
  - 価格 1e17 程度では例外にはならないが pips が -9999999999999986000 のような無意味な値になる。
- 修正案：parsePrice / parseLots に「現実的な上限」のエラーを足す（例：価格は 1,000,000 未満、ロットは 10,000 以下、整数部の桁数で判定）。あわせて calcProfitJpy の先頭で `Number.isSafeInteger(diffPoints)` などを確かめ、外れたら null を返す（例外で画面を止めない）。

### R-02（低）closeTrade / reopenTrade は「読んでから保存」の間に別の画面の変更を検出しない
- 該当：js/trades.js:343-347（closeTrade）、js/trades.js:355-359（reopenTrade）
- 何が起きるか：readLiveTrade（読み込みのトランザクション）と saveTrade（書き込みのトランザクション）が別なので、その間に別のタブ・別のウィンドウが決済・編集した場合、ALREADY_CLOSED の判定をすり抜けて後勝ちで上書きする（2つのタブで同時に決済を押す、など）。iPhone のホーム画面版は1画面なので実害はほぼないが、PC の複数タブで起こりうる。
- 修正案：closeTrade / reopenTrade から saveTrade に `expectedUpdatedAt: stored.updatedAt` を渡す。CONFLICT が返ったら読み直して ALREADY_CLOSED か再判定する。

### R-03（低）決済画面はタグ・メモを「画面を開いた時点の写し」で上書きする
- 該当：js/close-form.js:312-323（closeInputFromEvaluation が tags・memo を必ず渡す）、js/trades.js:166-167
- 何が起きるか：決済画面を開いたまま、別のタブで同じ記録のメモ・タグを編集して保存 → 決済画面で保存すると、buildClosedTrade は「保存されている最新の記録」に重ねるが、tags・memo は決済画面の古い写しで置き換えるため、別タブで直したメモ・タグが黙って元に戻る（画像は mergeImageIds で守られているが、メモ・タグは守られていない）。下書きの復元時は baseUpdatedAt で stale 判定されるが、画面を開いている最中の変更は検出されない。単一ウィンドウの iPhone では起きにくい。
- 修正案：R-02 と同じく closeTrade で expectedUpdatedAt（＝決済画面を開いたときの trade.updatedAt）を受け取り、違えば CONFLICT として「記録が変更されています」を出す。または決済画面で tags・memo を変更していないときは input に含めない（undefined にして保存済みの値を残す）。

### R-04（中）保存の途中に追加した画像が、記録に入らず黙って消える
- 該当：js/ui/image-field.js:340（whenIdle は呼んだ時点の queue しか待たない）、js/screens/entry.js:477-482・494-511（setSaving は保存ボタンだけ無効にし、「画像を追加」は押せるまま）。close.js:507-515、edit.js:663-670 も同じ形
- 何が起きるか：1枚目の画像を縮小中（iPhone で数秒かかる）に［保存］を押す → 「保存中」のまま whenIdle を待つ間に、利用者が「画像を追加」でもう1枚選べる。whenIdle は押した時点の queue だけを待つため、2枚目は縮小中（id が空）のまま getAddedIds() から外れ、記録はその画像なしで保存される。直後の images.dispose() で、2枚目は保存後に「画面が閉じた」と判断されて削除される。画面にはサムネイル（処理中）が出ていたのに、何の知らせもなく画像が付かない。縮小が保存より先に終わった場合は、記録にも下書きにも属さない画像が残り、1日後に掃除される（結果は同じく消える）。
- 修正案：(1) 保存中は imageField の「画像を追加」と × を無効にする（imageField に setDisabled(on) を足し、setSaving から呼ぶ）。(2) whenIdle を「処理中の枠が0になるまで繰り返し待つ」形にする（`while (items.some(i => i.origin === 'processing')) await queue;`）。(1)(2) の両方を推奨。

### R-05（低）updatedAt が秒単位のため、同じ秒の中の変更は CONFLICT で検出できず、決済が消えることがある
- 該当：js/trades.js:262（`stored.updatedAt !== expectedUpdatedAt` だけで判定）、js/screens/edit.js:681
- 何が起きるか：architecture 6.12 で既知の制約だが、起きたときの結果が重い。例：保有中の記録の編集画面を開いた「同じ秒」に別タブで決済 → 編集を保存すると expectedUpdatedAt が一致して通り、buildEditedTrade は「開いた時点の保有中の写し」を土台にするので、決済価格・損益が null の記録で上書きされる（決済の記録が消える）。単一ウィンドウの iPhone ではまず起きない。
- 修正案：updatedAt に加えて「土台にした記録そのもの」と保存されている記録を比べる（saveTrade に `expectedRecord` を渡し、updatedAt・syncStatus・syncedAt 以外を JSON で比較。edit.js は `base` を持っているのでそのまま渡せる）。スキーマ変更（revision 番号の追加）なしで済む。

### R-06（低）複数タブで同じ「新規」下書きを開いたとき、DUPLICATE を「保存済み」とみなして後の入力・画像が消える
- 該当：js/screens/entry.js:141（下書きの tradeId を引き継ぐ）、js/screens/entry.js:542-545（DUPLICATE を成功扱い）、js/ui/image-field.js:301-305（「この入力で追加した」画像を、記録に使われているか確かめずに物理削除）
- 何が起きるか：PC の2つのタブで同じ下書き（同じ tradeId）を復元 → タブAで保存 → タブBで内容を変えて保存すると DUPLICATE になり、「保存しました」と出るがタブBの変更は保存されていない。タブBで追加した画像は discardDraft で消える。さらにタブBで（タブAが保存した）追加済み画像の × を押すと、保存済みの記録が指している画像を物理削除してしまい、その記録は「読み込めません」になる。iPhone のホーム画面版（1画面）では起きない。
- 修正案：DUPLICATE のときは保存されている記録を読み、入力と中身が違えば「この記録は別の画面で保存済みです」と知らせて詳細へ移す（黙って成功にしない）。image-field の remove（added）は、discardDraft と同じ「どの記録の imageIds にも載っていない画像だけ消す」安全策を通す（drafts.js か images.js に `deleteUnusedImages(ids)` を用意して両方から使う）。

### R-07（低）saveTrade の deleteImageIds は、画像がその記録のものか確かめずに消す
- 該当：js/trades.js:276-277
- 何が起きるか：removeTradeImage（trades.js:388-389）は「image.tradeId がこの記録のときだけ」消すが、saveTrade の deleteImageIds は ID だけで消す。呼び出し側（編集画面・下書きの removedImageIds）の誤りや壊れた下書きで、別の記録の画像 ID が混ざると、その記録の画像を消してしまう（他の記録の imageIds は書き換えないので「指しているのに無い」状態になる）。現状の画面の流れでは混ざらないので低。
- 修正案：削除前に `ops.get(STORE.IMAGES, id)` で tradeId を確かめ、`image.tradeId === trade.id` のときだけ消す（removeTradeImage と同じ考え方）。

### R-08（低）自動保存の「同じ内容なら書かない」判定に removedImageIds が入っていない
- 該当：js/drafts.js:199
- 何が起きるか：snapshot が [fields, uiState, addedImageIds] だけなので、編集画面で一度下書きが保存されたあと「保存済みの画像を外す」だけの操作をしても、snapshot が前回と同じと判定されて下書きが更新されない。アプリが終了して復元すると、外した操作が失われる（画像は残る方向なので消失ではないが、入力が黙って戻る）。
- 修正案：snapshot に `draft.removedImageIds || []`（と baseUpdatedAt）も含める。

### R-09（低）年が 100〜999 の日時が保存形式（25文字固定）を壊す
- 該当：js/datetime.js:44-50（年の範囲チェックなし）、js/datetime.js:60-66（年を4桁にそろえない）
- 何が起きるか（Node で確認）：入力欄に「0500-01-01T10:00」と打つと fromInputValue が `500-01-01T10:00:00+09:00`（24文字）を返し、必須チェックを通って保存される。保存後は parseJst が読めず（null）、編集画面の日時は空欄、セッション null、文字列での並べ替え（一覧・CSV の entryAt 順）が崩れる。1000〜1999年や 9999年も警告なく保存できる。PC で年を打ち間違えたときに起こりうる。
- 修正案：dateFromJstFields で年を現実的な範囲（例 2000〜2099）に限定し、範囲外は null（＝「日時を入力してください」）にする。toJstString も `String(year).padStart(4, '0')` にしておく。

### R-10（低）削除直後の「取り消す」より先に、その記録の決済・編集の下書きが消される
- 該当：js/screens/list.js:617-648（loadDrafts が 'gone' の下書きを即削除）、js/draft-notice.js:43
- 何が起きるか：決済・編集の入力途中（下書きあり）の記録を詳細から削除 → 一覧に戻った時点で loadDrafts が「対象が削除済み」として下書き（と追加画像）を消す → 6秒以内に［取り消す］で記録を戻しても、入力途中の内容と画像は戻らない。
- 修正案：deletedAt が直近（例：1分以内）の記録の下書きは 'gone' でも消さずに残し、次回以降に消す。または削除の確認シートで「入力途中の決済・編集も破棄されます」と伝える。

### R-11（低）他の画面が古い版の DB を開いたまま（onBlocked）だと、保存が「保存中」のまま終わらない
- 該当：js/db.js:362-363（withTx が openDb を無期限に待つ）、js/screens/entry.js:514 ほか保存処理
- 何が起きるか：バージョンアップ待ち（onBlocked）の間は openDb が解決しないため、保存ボタンが「保存中」のまま固まる（下書きの読み込みには2秒の見切りがあるが、保存には無い）。お知らせ行「他の画面を閉じてください」は出るが、保存がどうなったか分からない。現在は DB_VERSION=1 なので、版を上げる将来のリリースで初めて起こりうる。
- 修正案：保存処理に見切り時間（例 10秒）を設け、超えたら「保存できませんでした［もう一度保存］」を出す（下書きは残っている）。

### R-12（低・要実機確認）CSV インジェクション対策の対象文字
- 該当：js/csv.js:48
- 何が起きるか：先頭の = + - @ タブ CR は対策済み（OWASP の推奨どおり）。全角の「＝＋－＠」や、先頭に空白を置いた「 =…」は対象外。日本語版 Excel が CSV を開くときにこれらを数式として扱うかは未確認。記録を書くのは本人だけなので実害は小さい。
- 修正案：T-35 の実機確認で Excel に「＝1+1」「 =1+1」のメモを持つ CSV を開いて確かめ、数式になるなら NEEDS_GUARD に `^[\s　]*['＝＋－＠=+\-@]` 相当を足す（unguardFormula も同じ規則に）。
