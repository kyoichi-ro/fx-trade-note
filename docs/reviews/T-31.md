## 指摘一覧

### S-01（低）SV-26 の不合格はテスト側の前提の問題（GPU で描くキャンバスだとノイズ画像が 1280px のまま 250KB 以内に収まる）
- 該当：tests/db.test.js:184-194（noiseJpegOf：2400x1600 のノイズ）、tests/db.test.js:1273-1287（SV-26 の「ノイズは 1024px のやり直しまで進む」）。処理側の js/images.js:381-399（prepareImage）・:95-107（encodeWithinLimit）は仕様どおり
- 何が起きるか（実測）：SV-26 は 2400x1600 のノイズを 1280x853 に**縮小してから**圧縮するが、縮小のときの補間（なめらかにする計算）がキャンバスの描き方で変わり、ノイズが平均化される度合いが違う。
  - ヘッドレス Chromium 141（キャンバスはソフトウェア描画）：1280px の品質 0.5 で 296KB → 250KB を超えるので 1024px でやり直し → 1024x683（合格）
  - 同じ Chromium で GPU 描画を有効（`--use-angle=swiftshader --enable-gpu-rasterization --ignore-gpu-blocklist`、chrome://gpu で「Canvas: Hardware accelerated」を確認）：1280px の品質 0.62 で 293KB、**品質 0.5 で 232KB → 250KB 以内なので 1280x853 で終わる**（「ノイズは 1024px のやり直しまで進む（実際：1280x853）」で不合格。不合格はこの1項目だけで、EXIF の向き6の確認は合格）
  - 普段使いの Chrome や確認用 Chrome は GPU でキャンバスを描くのが普通なので、同じ理由で不合格になったと考えられる（普段使いの Chrome そのものでは未確認）。
  - 処理は「1280px で 250KB 以内に収まれば、そこで終わる」（architecture 11.1）という仕様どおりに動いており、画像の縮小・保存の不具合ではない。テストが「ノイズは 1280px では必ず 250KB を超える」という、環境に左右される前提に立っているのが原因。
- 修正案（テストだけ直す。処理は変えない）：ノイズを**最初から 1280x853 で作る**（長辺が 1280px 以下なので 1280px の段では縮小が起きず、どの環境でもノイズのまま＝250KB を超える。1024px の段は縮小されるが、収まっても収まらなくても結果は 1024px になる。期待値は 1024x682 に変える：853×0.8＝682.4 のため。ソフトウェア描画・GPU 描画の両方で 1024x682・約234KB になることを実測で確認済み）。または期待値を「1280px で 250KB 以内に収まったか、1024px まで進んだか」のどちらかにし、どちらでも `blob.size > 0` と JPEG を確かめる形にする。

### S-02（中）ファイルを直して APP_VERSION を上げ忘れても、どのテストも気づかない（直したつもりの版がスマホに届かない）
- 該当：tests/release.test.js:180-187（RL-01 は「sw.js と config.js の値が同じか」だけを確かめる）、sw.js:22・js/config.js:12、手順は architecture 12.3・19.1
- 何が起きるか：Service Worker は「sw.js の中身が1バイトでも変わったとき」だけ新しい版を入れる。アプリのファイル（js/・css/・index.html）だけを直して公開し、両方の APP_VERSION を上げ忘れると、sw.js は前と同じなので新しい版は入らない。キャッシュ優先なので、スマホのアプリは**再読み込みしても・開き直しても古いファイルのまま**になる（PC の localhost は `?sw=1` なしで開くので直した版がすぐ見え、上げ忘れに気づきにくい）。T-33 の修正（R-04 の画像が消える件など）を公開したのに iPhone には届いていない、ということが起こりうる。いまの「リリース確認」8件は、両方の値が同じ（上げていなくても同じ）なら合格する。
- 補足：sw.js だけを直して（SHELL_FILES にファイルを足すなど）APP_VERSION を上げ忘れた場合は、新しい版は入るが**キャッシュの箱の名前が同じ**（`fxnote-shell-v0.1.0`）なので、インストールが動作中の古い版の箱を上書きし、開いている画面は新旧のファイルが混ざった状態になる。どちらの上げ忘れも RL-01 では見つからない。
- 修正案：ビルドなしでできる確認を「リリース確認」に足す。例 RL-06：Node のテストから `git` で「最後に公開したコミット（main の最新）」の sw.js・SHELL_FILES の中身を読み、今のファイルと比べて**1つでも中身が違うのに APP_VERSION が同じなら不合格**（「ファイルが変わっています。js/config.js と sw.js の APP_VERSION を上げてください」）。git が使えない環境ではこの1件だけスキップにする。あわせて architecture 19.1 の手順①に「どのファイルを直しても必ず上げる（sw.js だけの変更でも）」と明記する。

### S-03（低）起動に必要なファイルが1つでも読めない・書き間違いがあると、真っ白な画面のまま何も出ない
- 該当：index.html:50（`<script type="module" src="js/app.js">`）・index.html:57（`<main id="app"></main>` が空）、js/app.js:61-70（エラーの受け止めは app.js が動き出してから登録される）
- 何が起きるか（実測）：js/format.js の取得を失敗させて起動すると、画面は空白・`#notice-area` も空のまま（「予期しない問題が起きました」も出ない）。app.js と、そこから静的に読み込まれるファイル（app.js を含めて25個）のどれかが読めない・文法の誤りがあると、app.js 自体が実行されないため、window の error の受け止め（15.1）も登録されない。Service Worker のキャッシュが揃っていればまず起きないが、(1) 初回をオフライン気味の回線で開いた、(2) 公開した JS に文法の誤りがあった（Node のテストは app.js・router.js・画面ファイルを読み込まないので見つからない）ときに起きる。オーナーには「何をすればよいか」が分からない。
- 修正案：index.html の `<main id="app">` の中に、最初から固定の文（例「読み込んでいます…」「表示されない場合は、通信できる場所でアプリを開き直してください。」）を書いておく（router が描画時に置き換える。CSP に触れない）。さらに boot-theme.js（モジュールでない普通のスクリプト）で `document.addEventListener('error', (e) => { if (e.target.tagName === 'SCRIPT') … }, true)` を受け、モジュールの読み込み失敗時にその文を「読み込めませんでした［再読み込み］」に変える。

### S-04（低）別の画面で［更新］したあと、残った画面は「古いコード＋新しい画面ファイル」で動き続ける
- 該当：sw.js:197-211（activate で古い箱を消して clients.claim）、js/sw-update.js:104-110（別の画面で切り替わったときはお知らせ行だけ）、js/router.js:289（画面ファイルはそのつど import する）
- 何が起きるか（実測）：PC の2つのタブで、タブ2が入力中（#/new）のままタブ1で［更新］→ タブ2も新しい Service Worker の担当になり、古い箱は消え、タブ2には「アプリが別の画面で更新されました。再読み込みしてください。［再読み込み］」が出る（入力は残っていた：良い）。ただしタブ2で再読み込みせずに使い続けると、まだ開いていない画面ファイル（例 detail.js）は新しい版がキャッシュから読まれ、すでに読み込んだ共通のファイル（trades.js など）は古いまま組み合わさる。版の間で関数の名前や引数が変わっていると「画面を表示できませんでした」や、気づきにくい動きの違いになる。iPhone のホーム画面版は1画面なので起きない。
- 修正案：別の画面で切り替わったことを router に知らせ、次に画面を切り替えるとき、今の画面に未保存の入力がなければ `location.reload()`（新しい版で開き直す）にする。未保存の入力があるときは今のお知らせ行のまま。

### S-05（低）お知らせ行の［再読み込み］を入力の直後に押すと、最後の入力（約0.5秒分）が下書きに残らない
- 該当：js/app.js:47-53・81-83（［再読み込み］はすぐ `location.reload()`）、js/drafts.js:217-224（自動保存は0.5秒待ってから。pagehide の即時保存は、ページが閉じる前に書き込みが終わらない）
- 何が起きるか（実測：ヘッドレス Chromium）：#/new でエントリー価格に「151.234」を入れ、0ms・50ms・300ms 後に再読み込み → 3回とも入力は消え、下書きも無かった。1.5秒後なら残った。pagehide での flush() は IndexedDB の書き込みを始めるだけで、終わる前にページが閉じられる。入力画面にも出る「予期しない問題が起きました［再読み込み］」「アプリが別の画面で更新されました［再読み込み］」（#notice-area）で起こりうる。保存済みの記録には影響しない。iPhone で入力直後にアプリを上にスワイプして終了した場合も同じ可能性がある（実機は未確認）。
- 修正案：#notice-area の［再読み込み］は、router の今の画面に「下書きをすぐ保存して終わるのを待つ」関数（例 `flushDraft()`。entry/close/edit の autosaver.flush() を返す）があれば await してから reload する。sw-update.js の reloadOnce も同じ道具を通す。

### S-06（低）h() の「javascript: の URL を入れない」確認は、タブ・改行・制御文字を混ぜると通り抜ける
- 該当：js/ui/dom.js:17（`/^\s*javascript:/i`）・:52-54
- 何が起きるか（Node で確認）：`'java\tscript:alert(1)'`・`'\x01javascript:alert(1)'` は正規表現では false だが、ブラウザの URL の解釈では javascript: になる。いまは href・src に利用者の入力が入る箇所がなく（`#/trades/…` と blob: と固定の文字だけ）、CSP の `script-src 'self'` が javascript: URL の実行も止めるので、実害はない。Phase 2 以降で URL を画面に出すとき（Apps Script の URL など）に、この確認を頼りにすると危ない。
- 修正案：文字を `new URL(value, location.href)` で解釈してから `protocol` を見る形にし、`http:` `https:` `blob:`、または `#` で始まる相対だけを許す（許可するものを並べる方式）。

### S-07（低）オフラインで使う準備（キャッシュの保存）に失敗しても、利用者には分からない
- 該当：sw.js:148-161（precache の失敗はインストール失敗になるだけ）、js/sw-update.js:120-123（登録の失敗はコンソールだけ）、js/screens/settings.js の「このアプリについて」
- 何が起きるか（実測）：この origin の容量を 200KB に絞ると（CDP Storage.overrideQuotaForOrigin）、インストールが失敗して登録ごと消え、画面には何も出ない（オンラインでは普通に使える）。sw.js が 404 のときも同じくコンソールに警告が出るだけ。iPhone の空き容量が少ない状態で初めて開くと、オフライン（機内モード）では開けないのに、利用者はそれを知る方法がない。要件の「電波がなくても開いて記録できる」が黙って成り立たない。
- 修正案：設定画面の「このアプリについて」に「オフラインで使う準備：できています／まだできていません（通信できる場所でアプリを開き直してください）」の行を足す（`navigator.serviceWorker.controller` があり、`caches.has('fxnote-shell-v' + APP_VERSION)` が true なら「できています」）。
