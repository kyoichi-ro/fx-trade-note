## 1. この文書で使う言葉

| 用語 | 一言説明 |
|---|---|
| 絞り込み（フィルタ） | 条件に合う記録だけを表示すること。例：「本番だけ」「負けだけ」 |
| キーワード検索 | 入力した文字を含む記録だけを表示すること |
| AND / OR | AND＝「AかつB」（両方を満たすものだけ）、OR＝「AまたはB」（どちらかを満たせばよい） |
| 単一選択 / 複数選択 | 選択肢から1つだけ選ぶ / いくつでも選べる |
| サマリー | 一覧の上に出す、絞り込み結果の件数と合計損益の行 |
| 日本時間（JST） | 日本標準時（協定世界時＋9時間）。日本には夏時間がないので、常に＋9時間で計算できる |
| 半開区間 `[開始, 終了)` | 「開始は含み、終了は含まない」範囲。例：今日＝`[今日0:00, 明日0:00)`。境目の時刻が2つの期間に重複して数えられるのを防ぐ |
| 正規化 | 比べる前に文字の表記ゆれをそろえること。例：全角「ＡＢＣ」と半角「abc」を同じ文字として扱う |
| NFKC | 文字の正規化の国際ルールの1つ。全角英数字→半角、半角カタカナ→全角カタカナ、などをまとめて行える（JavaScript の `normalize('NFKC')`） |
| 部分一致 | 検索語が文章のどこかに含まれていれば一致とみなすこと。「ブレイク」で「ブレイクアウト」が見つかる |
| デバウンス | 文字を打つたびに毎回検索せず、入力が少し（0.25秒程度）止まってから1回だけ検索する工夫。動作が重くなるのを防ぐ |
| 擬似コード | 処理の流れを、実際のプログラムに近い形で書いた説明用のコード。本書の擬似コードは JavaScript で書いており、そのまま動く |
| インデックス（索引） | IndexedDB の中で、特定の項目（例：決済日時）で記録を素早く探すための目次。本の索引と同じ役割 |
| メモリ上で処理 | データベースから記録を一度まとめて読み込み、アプリの中（メモリ）で絞り込み・並べ替えをすること |

## 3. 共通ルール（一覧・分析で共通）

一覧のサマリーと、Phase 3 の分析画面で数字が食い違わないよう、次の約束を両方に適用します。

| # | ルール | 内容 | 根拠 |
|---|---|---|---|
| 1 | **論理削除した記録は対象外** | `deletedAt` に値がある記録は、表示・検索・件数・合計のどれにも含めない | requirements F-04、fx-rules 7章 |
| 2 | **保有中は損益の合計に含めない** | `status = open` の記録は件数には数えるが、損益（円）・pips の合計には入れない（損益がまだ決まっていないため） | fx-rules 4.5（open は `pips`・`profitJpy` が空） |
| 3 | **勝ち／負け／引き分けは損益（円）で判定** | 勝ち＝`profitJpy > 0`、負け＝`< 0`、引き分け＝`= 0`。手入力で上書きした値（`profitSource = manual`）も含め、保存されている `profitJpy` で判定する。pips や決済理由では判定しない。判定結果は保存せず毎回求める | fx-rules 7章（オーナー承認済み） |
| 4 | **日時は日本時間で区切る** | 「今日」「今月」などの境目、日付の見出し、曜日はすべて日本時間（JST）の0:00で区切る | requirements Q-08 |
| 5 | **合計は整数で足す** | 損益（円）は整数なのでそのまま足す。pips は `四捨五入(pips × 10)` で整数に直して足し、最後に10で割る（小数のまま足すと誤差が積み重なるため） | fx-rules 6.3 ルール6 |
| 6 | **デモと本番の損益は混ぜて合計しない** | 1つの画面にデモと本番の記録が両方あるときは、合計損益を**口座ごとに分けて**表示する。両方を足した金額は表示しない（練習の結果と本物のお金の結果が混ざると、振り返りの判断を誤るため） | requirements F-06、data-analyst 方針 |
| 7 | **表示の符号・桁** | 損益（円）は `＋12,345円` / `−3,210円` / `±0円`、pips は `＋25.3 pips` / `−8.0 pips` / `±0.0 pips`。マイナス記号は表示のみ「−」（U+2212） | design 6.3、fx-rules 6.1 |

## 4. 一覧画面（S-01）

### 4.1 全体の流れ

```
IndexedDB の trades ストア
   │ 起動時に1回まとめて読む（画像は読まない）
   ▼
メモリ上の記録一覧（論理削除を除外し、日時の数値・検索用の文字を前計算しておく）
   │ 絞り込み条件（4.2〜4.5）で選ぶ
   ▼
条件に合う記録
   ├─→ 並べ替え・日付ごとにまとめる（4.6）→ 画面のリスト
   └─→ 件数・合計損益を計算する（4.7）→ サマリー行
```

- 絞り込み条件を変えるたびにデータベースを読み直す必要はありません。メモリ上の一覧から選び直すだけです（4.9）。
- 保存・編集・削除・決済の後は、その記録だけメモリ上の一覧を更新（または全件を読み直し）してから再表示します。

### 4.2 MVP の絞り込み項目

**初期値**＝アプリを開いたとき・「すべて解除」を押したときの状態。初期値のときは「その条件では絞り込まない（すべて表示）」という意味です。

| # | 項目 | 対象の項目（キー名） | 選択肢 | 初期値 | 選び方 | 補足 |
|---|---|---|---|---|---|---|
| 1 | デモ/本番 | `accountType` | すべて／本番／デモ | **すべて** | 単一選択（セグメント切替） | 選択肢が2つしかないので「すべて」を含めた3択にする（複数選択と同じことができる）。初期値「すべて」は 6章 ①で確定 |
| 2 | 状態（status） | `status` | すべて／保有中／決済済み | すべて | 単一選択（セグメント切替） | 「保有中」を選ぶと決済済みは表示しない（逆も同じ） |
| 3 | 通貨ペア | `pair` | **記録に1件以上あるペア**だけを並べる。並び順は「よく使う通貨ペア」（設定 `favoritePairs`）の順 → それ以外はアルファベット順 | 未選択（＝すべて） | **複数選択**（チップ） | 記録がないペアは選んでも0件になるので出さない。論理削除した記録しかないペアも出さない |
| 4 | 売買方向 | `side` | すべて／買い／売り | すべて | 単一選択（セグメント切替） | 表示は design のとおり「▲ 買い」「▼ 売り」 |
| 5 | 期間 | 保有中＝`entryAt`、決済済み＝`exitAt` | すべての期間／今日／今週／先週／今月／先月／今年／期間を指定 | すべての期間 | 単一選択 | 詳細は 4.4 |
| 6 | 勝ち/負け/引き分け | `profitJpy`（3章ルール3で判定） | 勝ち／負け／引き分け | 未選択（＝すべて） | **複数選択**（チップ） | 1つでも選ぶと、**保有中の記録は自動的に対象外**（勝敗がまだないため）。「引き分け」の追加は 6章 ⑤で確定し、requirements F-03 も「勝ち/負け/引き分け」に更新済み |
| 7 | キーワード | `memo`・`entryReasons`・`tags` | 自由入力（最大100文字） | 空欄 | — | 詳細は 4.5 |

**「状態」と「勝ち/負け/引き分け」の組み合わせ**

| 状態の選択 | 勝ち/負け/引き分け のチップ | 理由 |
|---|---|---|
| すべて | 選べる。選ぶと保有中は自動で対象外になる。シート内に「勝敗で絞り込むと、保有中の記録は表示されません」と1行添える | 勝敗の絞り込みは決済済みにしか意味がないため |
| 保有中 | **選べない（灰色表示）**。すでに選ばれていた場合は選択を外す | 必ず0件になる組み合わせを作らせないため |
| 決済済み | 選べる | — |

**絞り込み中であることの表示**（design S-01 の「適用中の絞り込み条件チップ」用の文言）

| 項目 | チップの文言例 |
|---|---|
| デモ/本番 | 「本番」「デモ」 |
| 状態 | 「保有中」「決済済み」 |
| 通貨ペア | 「USD/JPY」（複数なら「USD/JPY・EUR/USD」、3つ以上は「USD/JPY ほか2」） |
| 売買方向 | 「▲ 買い」「▼ 売り」 |
| 期間 | 「今月（10/1〜10/31）」「10/13〜10/14」「10/13以降」「10/14まで」 |
| 勝敗 | 「負け」「勝ち・引き分け」 |
| キーワード | 「“ルール違反”」 |

- 絞り込みボタンに出す数字は、**初期値から変えている項目の数**（例：本番＋今月なら「2」）とします（design S-01「条件が付いていれば件数を表示」の具体化）。結果の件数はサマリー行に出すので、ボタンには出しません。
- **画面での見せ方は design 14.3.7・14.3.10 で確定**（T-07）：絞り込みシートの項目順は キーワード → 口座 → 期間 → 勝敗 → 状態 → 売買方向 → 通貨ペア（上の表の番号は項目の識別用で、画面の並びではない）。期間の表示名は幅の都合で「すべての期間」→「**全期間**」、「期間を指定」→「**指定**」と短くする（`filter` の値 `preset` は 4.10 のまま）。適用中の条件チップは**タップで確認なしにその条件だけを初期値に戻す**（2026-10-15 オーナー決定：design 14.7.9 ②）。シートの下部の「n件を表示」で条件を適用し、その時点で `listFilter` に保存する。

### 4.3 条件同士の組み合わせ

| 組み合わせ | ルール | 例 |
|---|---|---|
| **異なる項目どうし** | **AND**（すべてを満たすものだけ） | 「本番」かつ「今月」かつ「負け」 |
| **同じ項目の中の複数選択** | **OR**（どれかに当てはまればよい） | 通貨ペア「USD/JPY」または「EUR/USD」、勝敗「勝ち」または「引き分け」 |
| **キーワードの複数語**（空白区切り） | **AND**（すべての語を含むものだけ） | 「建値 指標」→ 「建値」と「指標」の両方を含む記録 |
| 論理削除 | 条件に関係なく常に除外 | — |

- 0件になったときは design 9.14 の「条件に合う記録はありません」＋［条件を解除］を表示します。

### 4.4 期間の指定

#### 4.4.1 どの日時で判定するか

| 記録の状態 | 判定に使う日時 | 理由 |
|---|---|---|
| 保有中（`open`） | **エントリー日時**（`entryAt`） | 決済日時がまだないため |
| 決済済み（`closed`） | **決済日時**（`exitAt`）（6章 ③で確定） | 損益が確定した日で数えると、サマリーの合計損益が「その期間に確定した損益」になり、業者の取引報告（確定損益の日付）とも考え方がそろうため。並び順・日付見出しも同じく決済日時（4.6）なので、画面の見た目と期間の判定が一致する |

- 例：9/30 21:00 にエントリーし 10/1 0:05 に決済した記録は、「今月（10月）」に入り、「先月（9月）」には入りません（4.11 の T08）。
- Phase 3 の分析で「エントリーした曜日・時間帯」別に見るときはエントリー日時を使います。どの分析でどちらを使うかは T-49 で決めます。

#### 4.4.2 期間の選択肢（すべて日本時間・半開区間）

例は「今」が **2026-10-15（木）12:00** のとき。

| 選択肢 | 範囲 `[開始, 終了)` | 例 |
|---|---|---|
| すべての期間（初期値） | 制限なし | — |
| 今日 | 今日 0:00 〜 明日 0:00 | 10/15 0:00 〜 10/16 0:00 |
| 今週 | **今週の月曜** 0:00 〜 来週の月曜 0:00 | 10/12（月）0:00 〜 10/19（月）0:00 |
| 先週 | 先週の月曜 0:00 〜 今週の月曜 0:00 | 10/5（月）0:00 〜 10/12（月）0:00 |
| 今月 | 今月1日 0:00 〜 来月1日 0:00 | 10/1 0:00 〜 11/1 0:00 |
| 先月 | 先月1日 0:00 〜 今月1日 0:00 | 9/1 0:00 〜 10/1 0:00 |
| 今年 | 1月1日 0:00 〜 翌年1月1日 0:00 | 2026/1/1 0:00 〜 2027/1/1 0:00 |
| 期間を指定 | 開始日 0:00 〜 **終了日の翌日** 0:00（開始日・終了日とも**その日を含む**） | 10/13〜10/14 → 10/13 0:00 〜 10/15 0:00 |

- **週の始まりは月曜**とします。FXの市場は月曜の朝に始まり土曜の早朝に終わるため、月曜始まりなら「1週間の取引」がひとつの週に収まります（6章 ②で確定）。
- **期間を指定**の入力：日付だけを選ぶ（時刻は選ばない）。開始日だけ・終了日だけの指定も可（「〜以降」「〜まで」）。開始日が終了日より後のときは**自動で入れ替えて**適用します（片手操作でやり直しをさせないため）。日付の選択には端末標準の日付入力（`<input type="date">`）を使う想定です（見た目は T-07）。
- 「今日」「今月」などは**画面を表示するたびに今の日時から計算し直します**。アプリを開いたまま日付が変わった場合に備え、アプリが前面に戻ったとき（`visibilitychange`）にも再計算します。
- **注意（日の区切り）**：日の区切りはカレンダーどおり日本時間の0:00です（Q-08）。深夜0:30の決済は「翌日」の記録になります。業者によっては取引日を朝6〜7時で区切るため、業者の日次報告とずれることがあります。

### 4.5 キーワード検索

#### 4.5.1 検索の対象

| 対象 | キー名 | 一致の仕方 |
|---|---|---|
| メモ | `memo` | 部分一致 |
| エントリー根拠 | `entryReasons`（配列） | それぞれの根拠に対して部分一致（「ブレイク」で「ブレイクアウト」が見つかる） |
| タグ | `tags`（配列） | それぞれのタグに対して部分一致 |

- 上記3つをまとめた「検索用の文字」に対して探します。複数語のときは、語ごとに**どこか1か所に含まれていれば**よい（例：「建値 指標」はメモに「建値」、タグに「指標前」がある記録に一致）。
- 項目の境目をまたいだ一致はしません（メモの末尾と根拠の先頭がつながって偶然一致する、ということは起きない）。
- **対象外**：通貨ペア・決済理由・感情・時間足などの選択項目（通貨ペアは絞り込みで選ぶ。感情・時間足などは Phase 3 の拡張絞り込みで対応）。

#### 4.5.2 表記ゆれの扱い（検索語と記録の両方に同じ処理をしてから比べる）

| 表記ゆれ | 扱い | 例 |
|---|---|---|
| 大文字／小文字 | **区別しない** | 「cpi」で「CPI」が見つかる |
| 全角／半角（英数字・記号・空白） | **区別しない**（NFKC で半角にそろえる） | 「cpi」で「ＣＰＩ」が見つかる |
| 半角カタカナ／全角カタカナ | **区別しない**（NFKC で全角にそろえる。濁点も1文字にまとまる） | 「ポンド」で「ﾎﾟﾝﾄﾞ」が見つかる |
| ひらがな／カタカナ | **区別しない**（カタカナをひらがなにそろえる） | 「さぽーと」で「サポート」、「ぽんど」で「ﾎﾟﾝﾄﾞ」が見つかる |
| 前後・連続する空白 | 前後の空白は無視、間の空白（全角・半角とも）は語の区切り | 「　建値　指標 」→「建値」「指標」の2語 |
| 漢字とかな | **区別する**（読みの変換はしない） | 「焦り」と「あせり」は別の文字として扱う |
| 長音「ー」 | そのまま比べる | 「サポート」の「ー」は変換しない |
| 記号（`.` `*` `(` など） | 普通の文字として扱う | 正規表現（パターン検索の仕組み）は使わない。入力をそのまま文字として探す |

- 文字を打つたびの検索はデバウンス（入力が0.25秒止まってから1回だけ検索）します。
- MVP では一致した部分の強調表示（ハイライト）はしません。検索語を画面に出すときは HTML として埋め込まない（XSS 対策、requirements 8章）。

### 4.6 並び順と日付グループ見出し

| グループ | 位置 | 並び順 | 同じ日時のときの順 | 日付の見出し |
|---|---|---|---|---|
| **保有中** | 一番上にまとめる（0件ならグループごと出さない） | **エントリー日時の新しい順** | `id` の昇順（毎回同じ順に並ぶようにするため） | なし（グループ見出し「保有中」のみ。各行にエントリー日時を月/日付きで表示） |
| **決済済み** | 保有中の下 | **決済日時の新しい順** | エントリー日時の新しい順 → `id` の昇順 | **決済日（日本時間）ごと**に見出し |

- **日付見出しの形式**：「10月15日（木）」。今年以外は年を付けて「2025年12月30日（火）」。見出しの下の行は時刻のみ（design 6.3）。
- **日付見出しの日計（その日の合計損益）**（T-07 で確定：design 14.3.5）：**サマリーが1口座のとき（＝条件に合う記録が本番だけ、またはデモだけのとき）だけ**日計を表示し、デモと本番が混在してサマリーが2行のときは表示しません（3章ルール6）。data-analyst の当初案（「本番」か「デモ」に絞り込んだときだけ）を、「絞り込んでいなくても記録が片方の口座だけなら出す」に広げたものです。日計は**円だけ**（pips は出さない）で、その日（日本時間）に決済した条件に合う記録の `profitJpy` を整数のまま足します。表示している行（最初の約50件）だけでなく、その日の条件に合う全件で計算します。判定は `summarize()` の結果で `byAccount.real.count` と `byAccount.demo.count` のどちらか一方だけが1以上なら「1口座」です。
- Phase 3 で並び替え（損益順など）を追加したときは、この「保有中を上・決済済みは新しい順」が初期の並び順になります。

### 4.7 サマリー（件数・合計損益）の計算

#### 4.7.1 計算方法

| 値 | 計算方法 |
|---|---|
| 対象 | 4.2〜4.5 の条件に合う記録（論理削除は常に除外） |
| 件数 | 対象の記録数。**保有中も含む**。内訳として保有中の件数も出す |
| 合計損益（円） | 対象のうち**決済済み**の `profitJpy` をそのまま足す（整数）。手入力値（`manual`）も含む。保有中は含めない |
| 合計 pips | 対象のうち**決済済み**の `pips` を `四捨五入(pips × 10)` で整数にして足し、最後に10で割る（小数第1位） |
| 口座ごとの分け方 | 上記をすべて**本番・デモ別々に**計算する（3章ルール6） |

- 1,000件で1件あたり最大でも数億円程度の損益を足しても、JavaScript の数値で誤差なく扱える範囲（約9×10^15）に十分収まるため、合計の足し算は通常の数値で行えます（BigInt は不要）。
- 決済済みなのに `profitJpy` が空、というデータは本来できません（requirements 6章で決済後は必須）。万一あった場合は合計にも勝敗にも含めず、件数にだけ数えます（データの不具合として reviewer が確認する対象）。

#### 4.7.2 デモと本番が混在するときの表示

**確定（6章 ①・案A）：口座ごとに1行ずつ出し、全体の合計損益は出さない**（件数の合計だけは出す）。

```
11件
[本番]  7件（保有中1）     −46,980円   ＋12.8 pips
[デモ]  4件（保有中1）      ＋1,543円   −19.7 pips
```

| 状況 | 表示 |
|---|---|
| 結果に本番とデモの両方がある | 上の例のとおり2行（本番を上、デモを下）。全体の行は件数のみ |
| 結果がどちらか一方だけ（絞り込みで選んだ場合も、たまたま一方しかない場合も） | その口座の1行だけ（バッジ付き） |
| ある口座に決済済みが1件もない（保有中だけ） | 合計損益と pips は「—」（**±0円とは表示しない**。「損益0円だった」と「まだ決まっていない」を区別するため） |
| 決済済みがあり合計がちょうど0 | 「±0円」「±0.0 pips」 |
| 0件 | 「0件」のみ＋空状態の表示 |

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A（採用）** | 混在時は口座別に2行 | 初期状態（すべて）でも両方の成績が一目で分かる。混ぜた合計は出ない | サマリーが2行になり、少し縦に場所を取る |
| B | 「デモ/本番」が「すべて」のときは合計損益を出さず、「口座を選ぶと合計を表示」と案内 | 1行で済む | 初期状態では合計が見えず、毎回口座を選ぶ手間がかかる |
| C | 混ぜて1つの合計を出す | 実装が簡単 | **採用しない**（練習と本番の損益が混ざり、判断を誤る） |

#### 4.7.3 pips の合計について

- pips の合計は、通貨ペアやロットの違いを考慮しない**単純な合計**です。例えば USD/JPY の 10pips と EUR/USD の 10pips は円に直すと金額が違い、0.1lot と 1lot でも金額は10倍違います。
- そのため **pips の合計と円の合計の符号が逆になることがあります**（例：4.11 の L-11 は円が −46,250円 なのに pips は ±0.0、L-21 は手入力の −30円 に対し pips は ＋0.5）。異常ではありません。
- 要件 F-03 に従い MVP では pips の合計も表示し、誤解を防ぐため**注記を表示します**（6章 ⑥で確定）。置き場所と文言は T-07 で確定しました（design 14.3.6）：**サマリーのグループの直下**に「**pips は通貨ペア・ロットを区別せず足した値です。**」（「通貨ペア・ロットの違いを考えない単純な合計」を幅375pxで1行に収まるよう言い換えたもの）。条件に合う決済済みが1件以上あり、サマリーに pips の合計が出ているときだけ表示します。

#### 4.7.4 一覧では出さないもの

- 勝率・平均損益・プロフィットファクターなどの指標は、一覧には出さず Phase 3 の分析画面（5章）で扱います（一覧はあくまで「探す・見返す」画面のため）。

### 4.8 絞り込み条件の保持

| 場面 | 条件を残すか | 方法 |
|---|---|---|
| タブ切替（一覧 → 設定 → 一覧）、詳細を見て戻る、決済して戻る | **残す** | アプリのメモリ上に持つ（design 4.3「スクロール位置と絞り込み条件は保持する」） |
| アプリを閉じて**30分以内**に開き直した | **残す** | 条件を変えるたびに端末（localStorage）へ保存時刻付きで保存し、起動時に30分以内なら復元 |
| アプリを閉じて**30分を超えて**から開き直した | **初期値に戻す** | 保存されている条件を使わない |

- **初期値に戻す理由**：一覧はアプリのホーム画面で、「今の保有中」を確認する場所でもあります。前回の「デモだけ」「先月」などが残ったまま開くと、**保有中の記録が隠れて決済を忘れる**、あるいは「記録が消えた」と勘違いするおそれがあります。
- **30分以内なら残す理由**：iPhone では業者アプリに切り替えた間にアプリが裏で終了させられることがあります（requirements F-01 の下書き保存と同じ事情）。振り返りの途中で業者アプリを確認して戻ってきたら条件が消えていた、を防ぐためです。
- 「今月」などは**選択肢の名前**で保存し、復元時に計算し直します。「期間を指定」は日付そのものを保存します。
- 保存の形（確定）：localStorage のキー `listFilter`（requirements 6.3。実際の保存キーは接頭辞付きの `fxnote:listFilter`：architecture 7.1）に `{ "version": 1, "savedAt": "<保存日時>", "filter": { …4.10 の filter… } }`。`savedAt` は architecture 6.6 の日時形式。読み込めない・形が違うときは黙って初期値を使います。
- 「よく使う条件に名前を付けて保存する」機能は Phase 3 の拡張（F-03「絞り込み条件の保存」）で扱い、ここでの「保持」とは別のものです。
- 30分という時間は 6章 ④で確定しました。下書きの自動復元（design 14.1.10・architecture 9.3）も同じ **30分** にそろえています。

### 4.9 1,000件でも速く動かすための方針

要件（requirements 8章）：記録1,000件・画像付きでも一覧の表示が1秒程度。

| # | 方針 | 理由 |
|---|---|---|
| 1 | **起動時に `trades` を1回だけまとめて読み込み（`getAll`）、絞り込み・並べ替え・合計はメモリ上で行う** | 1,000件の記録（画像を除く）は合計でも数MB程度。JavaScript で1,000件を絞り込む処理は数ミリ秒で終わるため、条件を変えるたびにデータベースを読むより速く、作りも簡単 |
| 2 | **画像（`images` ストア）は一覧では一切読まない** | 画像は1枚200KB前後あり、読むと一気に重くなる。一覧には画像を表示しない |
| 3 | 読み込み時に、比較に使う値を**前計算してメモリ上だけに持つ**：エントリー日時・決済日時の数値（ミリ秒）、検索用に正規化した文字 | 絞り込みのたびに日時の文字を解釈したり、文字を正規化したりしない。**この前計算の値は IndexedDB には保存しない**（データ構造を変えず、シート同期にも混ざらないようにするため）。記録を編集したらその記録だけ計算し直す |
| 4 | 日時の比較は**数値（ミリ秒）で行う** | 日時の文字（`2026-10-15T21:30:00+09:00`）をそのまま大小比較すると、`+09:00` 以外の形式（例：末尾が `Z`）が混ざったときに順番が狂うため |
| 5 | 画面への描画は**最初の50件程度**だけ行い、下までスクロールしたら続きを足す | 1,000行を一度に画面に作ると iPhone で重くなる。サマリー（件数・合計）は表示件数に関係なく**条件に合う全件**で計算する |
| 6 | キーワード入力はデバウンス（0.25秒） | 1文字ごとの再描画を避ける |
| 7 | 1,000件のダミーデータで計測する | T-31（reviewer）で iPhone 相当の環境で確認。遅ければこの表の 5 の件数を調整する |

#### IndexedDB のインデックス（2026-10-15 確定：architecture 6.3 と同じ）

T-04 時点では候補を9個（`status`・`entryAt`・`exitAt`・`syncStatus`・`updatedAt`・`accountType_exitAt`・`tags`・`entryReasons`・`pair`）、T-08 時点の architecture では5個（`status`・`entryAt`・`exitAt`・`syncStatus`・`deletedAt`）を挙げていましたが、pm が「実際に使う処理があるものだけ作る」方針で次のとおり統一しました。

| ストア | インデックス | 使う処理 | 作る理由 |
|---|---|---|---|
| `trades` | `syncStatus` | Phase 2 の未送信キュー（`pending`/`error` の記録だけを取り出す。architecture 3.3） | 未送信キュー専用のストアを作らず、このインデックスで取り出すと決めているため。Phase 2 で確実に使うので、DBのバージョンを上げる手間を省くため最初（v1）から作る |
| `images` | `tradeId` | あるトレードの画像をまとめて取り出す・孤立画像の掃除（architecture 11.6） | 画像は一覧のように全件を読み込まない（1枚200KB前後で重い）ため、トレード単位で探す索引が必要 |

**作らないもの（と理由）**

- 一覧（Phase 1）・分析（Phase 3）は**全件をメモリに読み込んで絞り込む**方式（方針1）のため、`status`・`entryAt`・`exitAt`・`pair`・`tags`・`entryReasons`・`accountType_exitAt` は使う処理がありません。
- `deletedAt`（削除済みだけを探す）・`updatedAt`（最近変更した記録）も、CSV・同期はメモリ上の全件か `syncStatus` で足ります。
- 将来、記録が非常に多くなって全件読み込みが遅くなった場合（T-31 の計測で判断）は、その時点でインデックスを足します。**インデックスの追加は既存データを壊さない安全な移行**（architecture 6.11）なので、後から足しても問題ありません。

**インデックスを使うときの注意（engineer 向け）**

- 値が `null` や未定義の記録は**インデックスに載りません**（エラーにはならず、単に索引から外れる）。そのため `exitAt` のインデックスには決済済みだけが載り、`deletedAt` にインデックスを作っても「削除済みの記録」しか探せません（「削除されていない記録」は探せない）。論理削除の除外はメモリ上で行ってください。
- `true`/`false`（boolean）はインデックスの値にできません。インデックスで探したい項目は文字か数値で持ちます（現在の 6章の項目はすべて対応済み）。
- 日時のインデックスで範囲検索する場合、日時の文字が**すべて同じ形式**（例：`YYYY-MM-DDTHH:mm:ss+09:00`、秒まで・ミリ秒なし・常に `+09:00`）である必要があります。保存時（と Phase 2 の CSV 読み込み時）に形式をそろえる処理を入れてください。

### 4.10 集計ロジックの擬似コード

engineer はこれと**同じ結果**になれば書き方は自由です。このコードは 4.11 のサンプルデータで実際に動かし、期待結果と一致することを確認済みです（4.11.4）。

```js
// ===== 絞り込み条件（初期値） =====
const DEFAULT_FILTER = {
  accountType: 'all',          // 'all' | 'real' | 'demo'
  status: 'all',               // 'all' | 'open' | 'closed'
  pairs: [],                   // 例 ['USD/JPY', 'EUR/USD']。空 = すべて（中は OR）
  side: 'all',                 // 'all' | 'buy' | 'sell'
  period: { preset: 'all', from: null, to: null },
  //   preset: 'all' | 'today' | 'thisWeek' | 'lastWeek' | 'thisMonth' | 'lastMonth' | 'thisYear' | 'custom'
  //   from / to: 'YYYY-MM-DD'（custom のときだけ。片方だけでも可）
  outcomes: [],                // 'win' | 'loss' | 'draw' の配列。空 = すべて（中は OR）
  keyword: '',
};

// ===== 日本時間の計算 =====
const JST_OFFSET_MS = 9 * 60 * 60 * 1000; // 日本時間 = UTC + 9時間（夏時間なし）
const DAY_MS = 24 * 60 * 60 * 1000;

// 日本時間の y年 m月（0始まり）d日 0:00 → 内部の時刻（ミリ秒）。
// d や m がはみ出しても（例：d = 0、m = -1）Date.UTC が前後の月・年に繰り越してくれる
function jstMidnight(y, m, d) { return Date.UTC(y, m, d) - JST_OFFSET_MS; }

// 内部の時刻 → 日本時間の 年・月（0始まり）・日・曜日（0 = 日曜）
// 端末のタイムゾーン設定に左右されないよう、getUTC系だけを使う
function jstParts(ms) {
  const d = new Date(ms + JST_OFFSET_MS);
  return { y: d.getUTCFullYear(), m: d.getUTCMonth(), d: d.getUTCDate(), dow: d.getUTCDay() };
}

// 'YYYY-MM-DD' → 日本時間のその日 0:00
function parseYmd(s) { const [y, m, d] = s.split('-').map(Number); return jstMidnight(y, m - 1, d); }

// 期間 → [開始, 終了)（開始を含み、終了を含まない）。null = すべての期間
function periodRange(period, nowMs) {
  const { y, m, d, dow } = jstParts(nowMs);
  const fromMonday = (dow + 6) % 7; // 月曜 = 0 … 日曜 = 6（週は月曜始まり）
  switch (period.preset) {
    case 'all':       return null;
    case 'today':     return [jstMidnight(y, m, d), jstMidnight(y, m, d + 1)];
    case 'thisWeek':  return [jstMidnight(y, m, d - fromMonday), jstMidnight(y, m, d - fromMonday + 7)];
    case 'lastWeek':  return [jstMidnight(y, m, d - fromMonday - 7), jstMidnight(y, m, d - fromMonday)];
    case 'thisMonth': return [jstMidnight(y, m, 1), jstMidnight(y, m + 1, 1)];
    case 'lastMonth': return [jstMidnight(y, m - 1, 1), jstMidnight(y, m, 1)];
    case 'thisYear':  return [jstMidnight(y, 0, 1), jstMidnight(y + 1, 0, 1)];
    case 'custom': {
      let { from, to } = period;
      if (from && to && from > to) [from, to] = [to, from]; // 逆順なら入れ替える
      return [
        from ? parseYmd(from) : -Infinity,
        to ? parseYmd(to) + DAY_MS : Infinity,             // 終了日はその日の終わりまで含める
      ];
    }
  }
}

// ===== キーワード検索 =====
// 表記ゆれをそろえる：NFKC（全角英数→半角、半角カナ→全角カナ）→ 小文字 → カタカナをひらがなに
function normalizeForSearch(s) {
  return String(s ?? '')
    .normalize('NFKC')
    .toLowerCase()
    .replace(/[ァ-ヶ]/g, (c) => String.fromCharCode(c.charCodeAt(0) - 0x60));
}

// 検索語 → 語の配列（全角・半角の空白で区切る。空なら []）
function toTokens(keyword) {
  return normalizeForSearch(keyword).split(/\s+/).filter(Boolean);
}

// ===== 読み込み時の前計算（メモリ上だけ。IndexedDB には保存しない） =====
function prepare(t) {
  return {
    ...t,
    _entryMs: Date.parse(t.entryAt),
    _exitMs: t.exitAt ? Date.parse(t.exitAt) : null,
    // 項目ごとに正規化して改行でつなぐ（項目の境目をまたいだ一致を防ぐ）
    _search: [t.memo, ...(t.entryReasons ?? []), ...(t.tags ?? [])].map(normalizeForSearch).join('\n'),
  };
}

// ===== 勝敗（fx-rules 7章） =====
// 実装では calc.js の judgeResult(trade)（architecture 13.1）と同じ関数を使い、二重に書かない
function outcomeOf(t) {
  if (t.status !== 'closed' || t.deletedAt || t.profitJpy == null) return null; // 判定対象外
  if (t.profitJpy > 0) return 'win';
  if (t.profitJpy < 0) return 'loss';
  return 'draw';
}

// 期間の判定に使う日時：保有中 = エントリー日時、決済済み = 決済日時
function baseTimeMs(t) { return t.status === 'open' ? t._entryMs : t._exitMs; }

// ===== 1件が条件に合うか（異なる項目どうしは AND） =====
function matchesFilter(t, f, range, tokens) {
  if (t.deletedAt) return false;                                              // 論理削除は常に除外
  if (f.accountType !== 'all' && t.accountType !== f.accountType) return false;
  if (f.status !== 'all' && t.status !== f.status) return false;
  if (f.pairs.length > 0 && !f.pairs.includes(t.pair)) return false;          // 中は OR
  if (f.side !== 'all' && t.side !== f.side) return false;
  if (range) {
    const b = baseTimeMs(t);
    if (!(b >= range[0] && b < range[1])) return false;
  }
  if (f.outcomes.length > 0) {                                                // 中は OR
    const o = outcomeOf(t);
    if (o === null || !f.outcomes.includes(o)) return false;                  // 保有中はここで外れる
  }
  if (tokens.length > 0 && !tokens.every((w) => t._search.includes(w))) return false; // 複数語は AND
  return true;
}

// ===== 並べ替え =====
function sortForList(list) {
  const byId = (a, b) => (a.id < b.id ? -1 : a.id > b.id ? 1 : 0);
  const open = list.filter((t) => t.status === 'open')
    .sort((a, b) => b._entryMs - a._entryMs || byId(a, b));
  const closed = list.filter((t) => t.status === 'closed')
    .sort((a, b) => b._exitMs - a._exitMs || b._entryMs - a._entryMs || byId(a, b));
  return { open, closed };
}

// ===== 決済済みを決済日（日本時間）ごとにまとめる =====
const WEEKDAYS = '日月火水木金土';
function dateLabel(ms, nowMs) {
  const p = jstParts(ms), n = jstParts(nowMs);
  return (p.y !== n.y ? `${p.y}年` : '') + `${p.m + 1}月${p.d}日（${WEEKDAYS[p.dow]}）`;
}
function groupClosedByDate(closed, nowMs) {
  const groups = [];
  for (const t of closed) {                       // closed は決済日時の新しい順に並んでいる前提
    const label = dateLabel(t._exitMs, nowMs);
    const last = groups[groups.length - 1];
    if (last && last.label === label) last.items.push(t);
    else groups.push({ label, items: [t] });
  }
  return groups;
}

// ===== サマリー（口座ごとに分けて計算。混ぜた合計は作らない） =====
// pips → 0.1pip 単位の整数（0から遠い方へ四捨五入。+ 0 で -0 を 0 にする）
const toTenths = (p) => Math.sign(p) * Math.round(Math.abs(p) * 10) + 0;

function summarize(list) {
  const empty = () => ({ count: 0, openCount: 0, closedCount: 0, profitJpy: 0, pipsX10: 0 });
  const s = { total: 0, byAccount: { real: empty(), demo: empty() } };
  for (const t of list) {
    const a = s.byAccount[t.accountType];
    s.total++;
    a.count++;
    if (t.status === 'open') { a.openCount++; continue; }  // 保有中は合計に入れない
    if (t.profitJpy == null) continue;                      // 本来ありえないデータ（4.7.1）
    a.closedCount++;
    a.profitJpy += t.profitJpy;                             // 円は整数のまま足す
    a.pipsX10 += toTenths(t.pips);                          // pips は整数にして足す
  }
  return s;
  // 表示：pips = pipsX10 / 10（小数第1位）。closedCount = 0 の口座は損益・pips を「—」。
  //       count = 0 の口座は行を出さない。本番 → デモ の順。
}

// ===== 一覧画面に渡すデータを作る =====
function buildListView(trades, filter, nowMs) {   // trades は prepare 済みの全件
  const range = periodRange(filter.period, nowMs);
  const tokens = toTokens(filter.keyword);
  const hits = trades.filter((t) => matchesFilter(t, filter, range, tokens));
  const { open, closed } = sortForList(hits);
  return { open, groups: groupClosedByDate(closed, nowMs), summary: summarize(hits) };
}
```

**実装上の注意**

- `Date.parse` には必ず**タイムゾーン付き**の日時文字（`+09:00` 付き）を渡してください。タイムゾーンなしの文字は、ブラウザによって解釈が異なることがあります。
- 日本時間の計算は `getUTC…` 系だけで行っています。`getHours()` などの端末のタイムゾーンに依存するメソッドを使うと、海外設定の端末で日付がずれます。
- 数値の比較・合計で `===` を使うのは整数（円・0.1pip 単位）どうしだけにしてください（fx-rules 6.3 ルール5）。
